## 1. 配置编译器：L1 → L2 → L3

### 1.1 为什么要三级

| 问题 | 只做 L2 的后果 |
|---|---|
| `"$.data.items[*]"` 每次渲染都重新字符串解析 | 一屏 20 卡片 × 6 字段 × 翻页 = 每秒上千次正则切分，掉帧 |
| 页面引用了不存在的 `feed` | 用户点进去才白屏，无法定位 |
| `fields` 里把 `title` 写成 `titel` | 静默不生效，卡片全是空白标题，排查 1 小时 |

L3 把这两类问题一次性解决：**路径预编译** + **引用完整性校验**。

### 1.2 编译管线

```kotlin
class ConfigCompiler(
    private val json: Json,
    private val validator: ConfigValidator,
    private val migrations: List<ConfigMigration>,
) {
    fun compile(rawText: String): Outcome<CompiledSchema> {
        // ── L1：语法层 ─────────────────────────────
        val element = runCatching { json.parseToJsonElement(rawText) }
            .getOrElse { return Outcome.Fail(Diagnostic.E001(it)) }

        if (rawText.length > MAX_SIZE) return Outcome.Fail(Diagnostic.E007("体积超限"))
        if (element.depth() > MAX_DEPTH) return Outcome.Fail(Diagnostic.E007("嵌套过深"))

        // ── 迁移：只在 Raw 层做，无需维护旧强类型模型 ──
        val migrated = migrations.fold(element) { acc, m -> m.applyIfNeeded(acc) }

        // ── L2：结构层（kotlinx.serialization 强类型）──
        val doc = runCatching { json.decodeFromJsonElement<UmpConfig>(migrated) }
            .getOrElse { return Outcome.Fail(Diagnostic.E002/E003(it)) }

        // ── L3：语义层（引用 + 路径语法 + scheme）──────
        val diagnostics = validator.validate(doc)
        if (diagnostics.hasBlocker()) return Outcome.Fail(diagnostics)

        return Outcome.Ok(CompiledSchema.from(doc, json))
    }
}
```

**关键点**：`CompiledSchema.from()` 里所有工作都是**一次性**的：

- `url` 模板切成 `[Literal, Var, Literal, Var...]` 片段数组
- JSONPath 字符串切成 `List<PathToken>`
- 正则 `pattern` 预先 `Regex.compile()`（避免运行期每次编译）
- `listSplit` 的分条正则同样在编译期编译，编译失败按 `E004` 处理（运行期不再有机会报错）
- `strip` 原样带到 L3，由管线在**解析之前**执行（配对写错只是配置错误，不需要每端各写一遍）
- `fields` 的键在编译期转成 `DomainField` 枚举（未知键直接 `E009`）

### 1.3 编译产物结构


## 2. JsonPath 引擎（`core:query`）

### 2.1 支持子集

```
$   .name   .*   [0]   [-1]   [*]   ..name   ['a b']
```

刻意不支持 `[?(...)]` 过滤器与切片 —— 这两者会让实现复杂度翻几倍，而实际影视接口用不到（需要过滤时用"全取 + 字段默认值 + required 跳过"兜底）。

### 2.2 词法 → 语法树

```kotlin
sealed interface PathToken {
    data class Field(val name: String) : PathToken
    data object Wildcard : PathToken                       // .* 或 [*]
    data class Index(val index: Int) : PathToken           // [n]，负数从尾部取
    data class Descend(val field: String) : PathToken      // ..name
}

object JsonPathCompiler {
    fun compile(expr: String): PathExpr {
        require(expr.startsWith("$")) { "JSONPath 必须以 \$ 开头" }
        val tokens = mutableListOf<PathToken>()
        var i = 1
        while (i < expr.length) {
            when (expr[i]) {
                '.' -> {
                    if (expr.getOrNull(i + 1) == '.') {          // ..name
                        val name = readName(expr, i + 2)
                        tokens += PathToken.Descend(name); i += 2 + name.length
                    } else if (expr.getOrNull(i + 1) == '*') {   // .*
                        tokens += PathToken.Wildcard; i += 2
                    } else {
                        val name = readName(expr, i + 1)
                        tokens += PathToken.Field(name); i += 1 + name.length
                    }
                }
                '[' -> { /* 解析 [n] / [-n] / [*] / ['key'] */ }
                else -> error("非法字符 '${expr[i]}' @ $i")
            }
        }
        return PathExpr(expr, tokens)
    }
}
```

### 2.3 求值（不可变、无副作用、可复用）

```kotlin
fun PathExpr.eval(root: JsonElement): List<JsonElement> {
    var current: List<JsonElement> = listOf(root)
    for (token in tokens) {
        current = when (token) {
            is PathToken.Field -> current.mapNotNull { (it as? JsonObject)?.get(token.name) }
            is PathToken.Wildcard -> when (current.firstOrNull()) {
                is JsonArray -> current.flatMap { (it as JsonArray) }
                is JsonObject -> current.flatMap { (it as JsonObject).values }
                else -> emptyList()
            }
            is PathToken.Index -> current.flatMap {
                val arr = it as? JsonArray ?: return@flatMap emptyList()
                val idx = if (token.index < 0) arr.size + token.index else token.index
                listOfNotNull(arr.getOrNull(idx))
            }
            is PathToken.Descend -> current.flatMap { collectRecursive(it, token.field) }
        }
        if (current.isEmpty()) return emptyList()      // 提前短路
    }
    return current
}
```

`PathExpr` 是不可变对象，被 `CompiledField` 持有，运行期只做遍历，**零字符串解析**。

### 2.4 关于 `root`

```kotlin
val scope = spec.root?.eval(responseJson)?.firstOrNull() ?: responseJson
val items  = spec.list?.eval(scope) ?: listOf(scope)
```

先定位 `root` 一次，后续 `list` 与所有 `fields` 都相对它求值 —— 既省开销又让配置可读。

## 3. 模板引擎（URL / headers 插值）

### 3.1 编译期切片

> **现状（M6.3 核对）**：真正落地的是 `core/source/TemplateEngine.kt`，一个正则 + `replace`，
> **不做编码、不支持任何修饰符**。下面这个 `TmplSeg` 是"带 `|raw` 修饰"的设计草案，**尚未实现**——
> 所以配置里写 `{{url|raw}}` 不会被替换掉，会原样留在 URL 里（`docs/03 §4.2`）。
> 需要编码的值，正确做法是在**注入方**编码（`{{keyword}}` 就是这么来的），不是靠模板层加修饰符。

```kotlin
sealed interface TmplSeg {                 // 草案，未实现
    data class Lit(val text: String) : TmplSeg
    data class Var(val name: String, val raw: Boolean) : TmplSeg   // {{url|raw}}
}

data class Tmpl(val segs: List<TmplSeg>) { // 草案，未实现
    fun render(scope: VarScope): String      // 变量缺失 → 空串
}
```

已实现版本（`TemplateEngine`）：

```kotlin
private val ref = Regex("""\{\{\s*([A-Za-z0-9_.]+)\s*\}\}""")
fun render(template: String, vars: Map<String, String>): String =
    ref.replace(template) { match -> vars[match.groupValues[1]] ?: "" }
```

### 3.2 变量作用域（按优先级由内向外查找）

```kotlin
class VarScope(private val layers: List<Map<String, String>>) {
    fun get(name: String): String? =
        layers.firstNotNullOfOrNull { it[name] }
}
// layers 顺序：[item, pageParams, filterValues, runtimeConst, builtins]
```

`item` 层在最前 → 嵌套请求里 `{{item.id}}` 能覆盖全局同名变量，符合直觉。

**页面参数的双写法**：`SourcePipeline` 在合并变量表时，会把传进来的参数**同时**注册成原名与 `p.xxx` 两个键，
所以配置里写 `{{p.channelId}}` 和 `{{channelId}}` 都能解析到同一个值。约定是页面参数统一写 `p.` 前缀（`{{p.category}}`），
而 `{{id}}`、`{{page}}`、`{{pageSize}}` 这类管线内置变量不带前缀——前者区分"来自页面的筛选条件"，后者是管线自己算出来的。
`config.schema` 里出现的 `{{p.*}}` 若在运行期没有对应参数，按空字符串渲染，不报错（加载期 `variablesOf()` 只做警告）。

**跨端约束（Android 上真踩过，装机即炸）**：变量匹配正则是 `\{\{\s*([A-Za-z0-9_.]+)\s*\}\}`，
结尾的 `}` **必须转义**。写成 `\s*}}` 在 OpenJDK 上合法，在 Android 上不合法——
Android 的 `java.util.regex` 底层走 ICU，未转义的 `}` 被当成残缺量词，
抛 `Syntax error in regexp pattern near index 27`；`ConfigCompiler` 把它包成 `SerializationException`
类的错误后，整份配置直接显示"配置加载失败"。桌面跑绿、装机全废，这条只能靠"两端都跑"发现。
`core:query` 里 `Extractors` 的同名正则（`{{$.path}}` 形式）有同一个坑，同批改掉了。

## 4. 抽取与变换

### 4.1 统一接口

```kotlin
interface Extractor {
    /** 从 payload 中抽出候选值（可能多个） */
    fun extract(payload: Payload, scope: Map<String, String>): List<String?>
}

sealed interface Payload {
    data class Json(val root: JsonElement) : Payload
    data class Text(val body: String) : Payload     // 纯文本整段；listSplit 切出来的"每一条"也是它
}
```

**刻意只有两态**。`text` 与 `html` 响应都装进 `Payload.Text`——HTML 不是一种独立的数据形态，只是一段文本，
差异交给下面这个能力接口：

```kotlin
fun interface HtmlSelector {                          // 宿主能力，不是 payload 态
    fun select(source: String, selector: String, attr: String?): String?
}

val NoHtmlSelector = HtmlSelector { _, _, _ -> null } // 没有 HTML 能力的端：css 抽取器退化为空（对应 W003）
```

这样做的收益：`core:query` 在 JVM 上可以零依赖跑测试（不需要 Jsoup）；`kind=css` 的配置在任何端都能**被导入并通过校验**，
只是运行期在没有 `HtmlSelector` 的端返回空值——正是 `W003`（平台能力不足，降级而非阻断）想表达的行为。

`CssExtractor` 的实现细节：`Payload.Text` 原样、`Payload.Json` 先转成字符串，再交给 `HtmlSelector`。
这也是"文本通路"能复用 `regex` 抽取器的前提：切出来的每条记录就是一个 `Payload.Text`。

实现清单：`JsonPathExtractor` / `RegexExtractor` / `CssExtractor` / `DelimitedExtractor` / `TemplateExtractor` / `ConstExtractor`。

| 抽取器 | 在 `Payload.Text` 上的行为 |
|---|---|
| `jsonPath` | 返回空（没有 JSON 树） |
| `regex` | 正常匹配 |
| `css` | 交给 `HtmlSelector`，无实现则空 |
| `delimited` | 拿整段文本当 `raw`，逐级切 |
| `template` | 只有 `{{name}}` 能从作用域取值，`{{$.path}}` 为空 |
| `const` | 常量本身就是结果 |

### 4.2 `from` 为数组 = 多候选短路

```kotlin
class MultiCandidateExtractor(
    private val candidates: List<Extractor>,
) : Extractor {
    override fun extract(payload: Payload, scope: Map<String, String>): List<String?> {
        for (c in candidates) {
            val v = c.extract(payload, scope).firstOrNull { !it.isNullOrBlank() }
            if (v != null) return listOf(v)
        }
        return listOf(null)
    }
}
```

> 这是配置里最实用的兜底手段："主字段 + 备用字段"，两个接口版本并存时不用改配置。

### 4.3 变换链执行顺序（**顺序固定，不可调**）

```
raw string
  → trim
  → rewrite[]        正则替换（可多条）
  → map              枚举映射（命中即替换，未命中保留原值）
  → prefix + value + suffix
  → type cast        string/int/float/bool/stringList/long
  → default          全空兜底
```

```kotlin
class TransformChain(private val steps: List<TransformStep>) {
    fun apply(raw: String?, ctx: EvalContext): Any? {
        var v: String? = raw
        steps.forEach { v = it.run(v, ctx) }
        return v
    }
}
```

**为什么顺序固定**：如果顺序可变，"先拼前缀再 map" 与 "先 map 再拼前缀" 的结果完全不同，用户会陷入玄学。固定后文档写明即可。

### 4.4 条目级失败隔离

```kotlin
fun mapItem(scope: JsonElement, spec: CompiledResource): MediaSummary? {
    var failed = false
    val m = mutableMapOf<DomainField, Any?>()
    for ((field, cf) in spec.fields) {
        val v = runCatching { cf.eval(scope) }
            .onFailure { trace.record(ExtractFailed(field, it)) }
            .getOrNull()
        if (v == null && cf.isRequired) failed = true
        m[field] = v
    }
    if (failed) return null            // 该条跳过，计入 skipped 计数
    return MediaSummary.from(m)
}
```

页面展示时：`已加载 18 条（2 条因必填字段缺失被跳过）` —— 让问题可见，而不是静默丢数据。

## 5. 数据管线执行（`core:source`）

### 5.1 五阶段

```
① BUILD    模板渲染 URL / Header / Body
② HTTP     发送请求，读取字节流，按 encoding 解码
③ LOCATE   解析为 Payload（json/text/html）：先 strip 剥壳，再按 listSplit / root 定位
④ EXTRACT  遍历 list，逐条映射 fields → 域模型
⑤ PAGING   解析 hasMore / cursor
```

每阶段产出 `StageResult`，失败会带上阶段标签：

```kotlin
sealed interface Stage { BUILD, HTTP, LOCATE, EXTRACT, PAGING }

data class StageResult<out T>(
    val data: T?,
    val error: StageError?,
    val timings: Map<Stage, Long>,
)
```

### 5.2 主流程

```kotlin
suspend fun loadFeed(
    resource: CompiledResource,
    params: FeedParams,
): StageResult<PagedResult<MediaSummary>> = coroutineScope {
    val t0 = now()

    // ① BUILD
    val req = buildRequest(resource.request, scopeOf(params), schema.runtime)
    trace.request(req)

    // ② HTTP（带缓存 + 重试）
    val resp = http.fetch(req)                      // 失败 → E100，非 2xx → E101
    trace.response(resp)

    // ③ LOCATE
    val payload = decode(resp, resource.responseType)   // json/text/html
    val scope   = resource.root?.eval(payload.json)?.firstOrNull() ?: payload.json

    // ④ EXTRACT
    val nodes = resource.list?.eval(scope).orEmpty()
    val items = nodes.mapNotNull { mapItem(it, resource) }

    // ⑤ PAGING
    val hasMore = resource.paging?.hasMore?.eval(scope)?.asBool()
        ?: (items.size >= params.pageSize)

    StageResult(PagedResult(items, params.page, hasMore), null, timings)
}
```

**两条通路的分叉点**

`responseType` 与 `listSplit` 决定 LOCATE 阶段走哪条：

| 响应形态 | LOCATE 产物 | `list` 的来源 | 详情如何定位 |
|---|---|---|---|
| JSON / AUTO | `Payload.Json` + `root` 定位 | `list` 路径求值 | `root` 定位后取单对象 |
| TEXT / HTML（声明了 `listSplit`） | 一串 `Payload.Text` | `listSplit` 每命中一次切一条 | 取第一条命中（没有按 id 过滤的能力） |

实现要点：

- `strip` 在任何解析之前执行，顺序固定为 `trim → 去 prefix → 去 suffix → trim`。会员视频示例源 `示例站点/详情接口` 的 `VAR={...};` 这类外壳就是靠它变成合法 JSON 后再走 `root`/`list`。
- 文本通路上没有 JSON 文档，`paging.hasMore` 这类路径表达式不可求值，`resolveHasMore` 退化为 `maxPage` + 非空兜底。这是**明确的能力边界**，不做假支持。
- `detail` 在文本通路只能取第一条命中。示例视频源没有按 id 取单条的公开接口，所以 `samples/` 里的长视频示例配置 在 `meta.description` 里写明"详情只有频道最新一条"，真正的按 id 取详情留给 M4 接入 oEmbed 后替换。
- 文本通路复用已有 `regex` 抽取器，不引入 XML 解析库——保持"受控抽取器集合"这条约束不变。

### 5.2.1 测试基线：站点数据只有一个来源

站点级测试（配置编译、管线抽取、播放地址拼接）一律读仓库里的 `samples`，不再各自内联假 JSON：

| 数据 | 位置 | 被谁消费 |
|---|---|---|
| 站点配置 | `samples/*.json` | `SampleConfigTest`（全部样本必须编译零错误）、`SamplePipelineTest` |
| 真实响应快照 | `samples/fixtures/` 里的文本 feed 快照、`samples/fixtures/` 里的详情接口快照 | `SamplePipelineTest`（MockEngine 原样回放） |
| 参考校验器 | `tools/validate_config.py samples/*.json` | 与 `core:config` 的 Kotlin 校验器互为交叉验证 |

`core:query` 的 44 例是路径语法与抽取器的算法用例（`$..name`、`[0]`、`[-1]`、候选短路等），不依赖站点响应，因此保持内联；凡涉及"某个网站返回什么"的断言，都不允许再内联。

### 5.2.2 请求头默认值与系统代理（四个真实踩过的坑）

改成"在线请求"之后，桌面端连续踩了四次，每次都换了错误码，值得逐条记下来：

| 现象 | 真实原因 | 处理 |
|---|---|---|
| 桌面端 `[E010] Connection timed out`，而同一个 URL 在 PowerShell 里 200 | **JVM 默认不看系统代理**。Clash 这类工具只改 Windows 的"Internet 设置"，Java 进程默认直连 | 桌面端 `main()` 在 `launchApp()` 之前 `System.setProperty("java.net.useSystemProxies", "true")`。Android 不需要（跟随系统网络） |
| 代理生效后变 `[NET] HTTP 404` | 请求没带 `User-Agent`。Google 对"看不出是浏览器"的请求直接 404（不是 UA 内容被拒——`okhttp/4.12.0` 在 PowerShell 里同样是 200） | `HttpFetcher` 补默认 `User-Agent` + `Accept-Language` |
| 详情页 `[NET] HTTP 404 ... channel_id=` | 详情页没声明 `params`，`{{p.channelId}}` 渲染成空串 | 详情页 params 为空时复用列表页的站点级参数（见 §7.6） |
| 切到国内站点后 `[E010] Remote host terminated the handshake` | 开了系统代理之后，**国内 CDN 拒绝经 HTTP 代理隧道进来的 TLS 握手**。同一 URL 直连 OK、JDK 自带 HttpClient 走同一代理也 OK，只有 OkHttp 经隧道这条链路失败（强制 TLS 1.2 + HTTP/1.1 同样失败），因此排除 TLS 版本与 UA | 按配置的 `runtime.proxyBypass` 把该站域名改走 `DIRECT`（见下） |

**第四条坑为什么不能用现成开关**：`http.nonProxyHosts` 在 `java.net.useSystemProxies=true` 下**被忽略**，
写了 `*.example.com` 依然走代理。唯一有效的做法是包一层 `ProxySelector` 自己分流：

```kotlin
// app/desktop/ProxySupport.kt —— 域名后缀来自配置的 runtime.proxyBypass
ProxySelector.setDefault(object : ProxySelector() {
    override fun select(uri: URI): List<Proxy> {
        val host = uri.host ?: return system.select(uri)
        val direct = bypass.any { host.equals(it, true) || host.endsWith(".$it", true) }
        return if (direct) listOf(Proxy.NO_PROXY) else system.select(uri)
    }
    override fun connectFailed(uri: URI, sa: SocketAddress, e: IOException) = system.connectFailed(uri, sa, e)
})
```

**这条策略是开发期便利，不是产品能力**：Android 走系统网络栈、不读这个字段；
正式版桌面端若要让用户自填代理，属于 `docs/05` M7 的范围，本期不做。

请求头的合并规则写在一行里，配置永远优先：

```kotlin
// DEFAULT_HEADERS 在左，requestHeaders 在右 → 同名键后者覆盖前者
(DEFAULT_HEADERS + requestHeaders).forEach { (k, v) -> header(k, v) }
```

默认头只有 `User-Agent` 与 `Accept-Language` 两个，**不做更多"伪装"**。
再加 `Sec-Fetch-*`、`Referer`、Cookie 那一套属于反爬对抗，不在本项目目标里；
真遇到某站必须带特定头，写进该站配置的 `request.headers` 即可——那是配置的责任，不是引擎的。

### 5.2.3 分页参数注入：`paging.param / startAt / step` 的唯一落点

`SourcePipeline.list(key, page, extra)` 里这一行决定了"配置写的分页到底生不生效"：

```kotlin
val vars = variables(extra) + pagingVars(res.paging, page, extra)
```

**曾经只有后半截，且写死成 `("page" to page.toString())`。** 后果很隐蔽：`paging.param`（比如站点要 `offset`）、
`paging.startAt`（比如站点第一页是 0）、`paging.step`、`mode: offset` **全部被静默忽略** ——
配置里写得再对，URL 里也永远只有 `page=1,2,3…`，站点拿到不认识的参数就把同一批数据反复返回。
界面看起来"能滚动加载"，但每次都是同一屏内容，且 `hasMore` 还因为"本次结果非空"一直为 true。

`pagingVars` 的口径（与 `docs/03 §5.3` 的表一致）：

| `mode` | 注入名 | 值 |
|---|---|---|
| `page` | `param`（默认 `page`） | `startAt + (page-1)*step` |
| `offset` | `param`（默认 `offset`） | `(page-1)*pageSize` |
| `cursor` | `param` | `extra["cursor"]` 原样透传 |

三条设计取舍：

- **同名就覆盖**：`param` 是 `page` 时直接覆盖逻辑页码。这样 `startAt: 0` 的站点第一页真的传 `0`，
  而不是"配置说从 0 开始、代码执意传 1"。
- **不同名就并存**：`param` 是 `offset` 时额外保留 `{{page}}` = 逻辑页码（第几页），
  两种表达都能在 URL 里引用，也能在同一份配置里混用。
- **`cursor` 不自动串联**：管线是无状态的，它不替谁记住上一页返回的游标。要真做游标分页，
  UI/会话层得把游标透传进 `extra` 并跨请求保存 —— 当前首页只做页码翻页，所以这里只做参数透传，
  不做假串联（宁可写得少，也不写得像能用其实不能用）。

### 5.2.4 分页实测（2026-11-11）

"配置能表达分页"和"站点真的给分页"是两件事，两件都测过：

| 对象 | 观察 | 结论 |
|---|---|---|
| 频道页不带参数 / 带 `?offset=15` / 带 `?offset=0&pagesize=30` | 三组返回的条目 id 集合完全相同（各 15 条，去重后比对） | 频道页的 `offset`/`pagesize` 是前端展示参数，SSR 里只有首屏，**没有翻页** |
| 首页 `?page=1` 与 `?page=2` | 各 14 条，条目 id 集合完全相同 | `page` 参数同样无效 |
| `?page=3` 相对 `page=1` | 14 条里有 2 条不同 | 不是分页，是 SSR 里推荐位的随机漂移 |
| 列表接口的带签名分页形态（两种写法） | 均 404 | 带签名的频道分页接口不在能力范围内 |

应用内实测（桌面端，滚到列表底部触发 `onLoadMore`，日志为 `[feed]` 前缀）：

```
[feed] loadMore homeFeed page=2 已有=14          ← 渲染层的 GridPagingEffect 确实触发了
[feed] page=2 返回=14 新增=1 站点hasMore=true 判到底=false
[feed] loadMore homeFeed page=3 已有=15
[feed] page=3 返回=14 新增=0 站点hasMore=true 判到底=true   ← 整页无新增 → 判到底，停
```

这段日志解释了两件事：① "滚动到底会不会真的发第 2 页请求"——会；② 为什么必须有"整页无新增即到底"这层兜底：
站点 `hasMore` 在文本通路上只能靠"本次结果非空"（永远是 true），没有这层兜底就会一路翻到 `maxPage`，
把同一屏内容重复追加 4 遍（14 条 → 70 条）。所以它不是可选优化，是文本通路的**必要**终止条件。

### 5.2.5 详情分组：`episodes` 与 `tracks` 两条通路并列（M4.1 / M4.2）

`detail(key, id, extra, trackKey)` 是详情取数的唯一入口，第四参 `trackKey` 来自
`pages[].layout.tracks`（引用 `resources.tracks` 的键）。内部把两批 `TrackGroup` **相加**：

```kotlin
val groups = loadEpisodeGroups(res, payload, vars, id) +   // ① id 表 → 逐条二次请求
    buildSpecTrackGroups(trackKey, payload, summary.kind, vars)  // ② 响应内直接切分
```

| 通路 | 数据形状 | 典型源 | 失败行为 |
|---|---|---|---|
| `episodes` | 先拿 id 表，再逐条 `详情接口`（示例视频源） | 示例视频源剧集 | 任一条失败只丢该条；整批失败只丢这一组，详情主体照出 |
| `tracks` | 响应里本来就是"整串"或"数组" | CMS 系接口、图集 | 纯本地切分，不发达请求，不会失败 |

两者可并存：一部剧既有"线路串"（`tracks` 切出 3 条线路），又有"逐条取数的选集"（`episodes`），
得到的是 `线路1/线路2/线路3 + 选集/预告/花絮` 一共 6 个 chip。切 chip **只切视图不重取数**——
数据在详情那一次响应里已经齐了，切一次不发请求是这层的核心承诺。

`tracks` 侧两种形态的实现在 `delimitedGroups` / `arrayGroups`，契约见 `docs/03 §7.3`。
落地时踩到的三个坑（都不是"写错一个字符"，而是"能跑但结果是错的"）：

| 坑 | 现象 | 根因 | 修法 |
|---|---|---|---|
| `asText()` 不存在 | 编译期报错 | `JsonPrimitive.content` 才是取值入口，`asText()` 是别的库的 API | 统一 `(it as? JsonPrimitive)?.content` |
| `{{imageBase}}` 没渲染 | 图片全 404，但**不报错** | `array` 的 `prefix` 不走资源 `fields` 那条渲染通路 | `arrayGroups(..., vars)` 里对每个字段 `copy(prefix = templates.render(...))` |
| `groupSplit` 全切 | 组数比配置多 | `"a$$$b$$$"` 用 `split` 会在尾部切出空段 | 用 `indexOf` 只切第一次 |

### 5.2.6 选集缓存的落盘时机

缓存是 `key#N` 切片 + `key#n` 片数 + `key#ts` 写入时刻三段。三段都写完后**必须 `flush()`**：

```kotlin
prefs.putInt("$key#n", i)
prefs.putLong("$key$EPISODES_CACHE_TS_SUFFIX", nowMs())
runCatching { prefs.flush() }   // ← 不加这行，进程被 run 任务结束/强杀时会只落切片
```

`java.util.prefs.Preferences` 的写入是异步落到注册表的。实测遇到过"切片和片数都在、只有 `#ts` 缺"的记录：
读侧按"无时间戳 = 过期"处理，于是下一次进详情又重拉一遍——功能没坏，但缓存等于白写。
这也解释了为什么"缓存命中率看起来不稳定"。

### 5.2.7 播放目标的三种切换：换集 / 切线路 / 自动连播

视频内容页持有的不是"一条 `Track`"，而是 `PlayTarget(summary, groups, groupIndex, trackIndex)`
——**当前这一条 + 它所在的全部分组**。原因很直接：自动连播要知道"下一集是谁"，
线路切换要知道"同一集在另一条线路上是哪一条"，两件事都要求把整组带进来。

| 动作 | 谁算 | 怎么落到播放器 |
|---|---|---|
| 用户在内容页点某一集 | `ContentRoute` 的 `UmpTrackSections` 回调求 `gi/ti` | 新建 `PlayTarget` → `selectedTarget`，同一 `ContentRoute` 内更新 |
| 线路切换 | `LineMenu` → `PlayTarget.switchLine(i)` | 同页更新 `selectedTarget` |
| 自动连播 | `PlayerStatus.ENDED` → `target.next()` | 同页更新 `selectedTarget`，不重建 facade |

**路由层不持有"当前是哪一集"**：它只负责播传入的 `target`，任何变化都回传宿主。
这条约束换来的是"状态只有一份"，不会出现"播放器在播第 8 集、标题写着第 6 集"这种错位。

三处关键实现细节：

- **`remember(item.id)` 建 facade**：只按条目 id 建，换集/切线路**不重建播放器**。
  重建会打断缓冲、丢掉倍速与音量，用户看到的是"闪一下重新加载"。
  重建的边界只在"换另一个剧"时发生。
- **ENDED 的顺序必须是先 `clear(key)` 再 `next()`**：反过来的话，连播结束时心跳那一路
  可能把"已播完"的位置又写回库里，下次进这一集直接从结尾起播。
- **心跳与离场补写用 `rememberUpdatedState(key)`**：`LaunchedEffect(key)` 里捕获的是
  进入时的旧键，换集之后必须拿到新键，否则第 8 集的进度会写到第 6 集的键上。

#### `index` 的语义差异（跨组切线路为什么会落到第 1 条）

`switchLine` 按**集号**（`Track.index`）对齐，不按下标：不同线路的组不一定等长，
按下标对齐会"跳到别的集"。但两种通路的 `index` 语义不同：

| 通路 | `index` 是什么 | 跨组切线路的结果 |
|---|---|---|
| `tracks`（多线路形态） | 组内的第几条 | 对齐有效，切到的是同序号那条 |
| `episodes`（选集/预告/花絮） | **id 表里的全局序号**（`fetchTrack(i + 1, id)`） | 选集组里没有预告的序号 → 找不到 → 退化为第 1 条 |

第二种"退化"恰好是对的：**正片和预告本来就没有"第几集"的对应关系**，
从"预告6"切到"选集"线路应落在选集第 1 条，而不是"选集第 6 集"。
模拟器实测即此结果（`线路2 ▾` → 选「选集」→ 标题变「剧名_01」、时长 03:25、从头起播），
同一轮也观察到预告片_06 在播完后自动接到 07、08（连播只接同组下一集）。

### 5.2.8 第二个 `episodes` 站点带来的三处待办（示例短剧源，2026-11-14）

`samples/` 里的短剧示例配置是第一个"每集地址必须 POST 才给"的源。配置侧已经能跑通
（`ids` 用 `$.episodes[*].ep_num`、`item.request` 是 `POST` + `{}`，口径见 `docs/03 §5.5.4`），
但它把三个"现在能凑合、迟早要改"的点暴露出来了。三条都**不是配置能解决的**，按影响排序记在这里。

#### (1) 选集缓存 TTL 必须能按源配置（直接影响播放成功率）

`EPISODES_CACHE_TTL_MS = 6h` 是硬编码的。对"地址长期有效"的源这是对的；
对示例短剧源是错的——`streams.main` 的 `auth_key` 只活**约 2 小时**，于是缓存命中的恰恰是**已过期**的地址。
用户路径很短：上午进过一次详情 → 下午再进 → 选集秒出 → 点第 3 集 → `P2007`。
现象长得像"播放器坏了"，实际是"缓存太长寿"。

改法三处，都是**加参数不改语义**：

```kotlin
// core:model/ConfigModels.kt
data class EpisodesSpec(…, val cacheTtlMs: Long = 21_600_000L)   // 缺省仍是 6h

// core:source/SourcePipeline.kt · loadEpisodeGroups
val ttlMs = res.episodes.spec.cacheTtlMs.coerceIn(60_000L, 7L * 24 * 3600 * 1000)

// core:storage/EpisodesCache.kt
interface EpisodesCache {
    fun read(key: String, ttlMs: Long = EPISODES_CACHE_TTL_MS): String?
}
```

`ttlMs` 缺省值让老配置行为完全不变（`docs/03 §16.3` 第 1 条）。示例短剧源配 `5400000`（90 分钟）。
配套的口径要写进校验器：`cacheTtlMs > 0` 且"地址带 `auth_key`/`vkey` 的源建议 ≤ 签发有效期"——

> 另一条同源经验：这类"签名地址"不只是选集受影响，`playUrl` 存在列表条目里时也一样（`docs/03 §5.5.4` 的 (3)）。
> 判断依据不是"哪个字段"，而是"这条 URL 里有没有时间戳"。

#### (2) 详情页没有「播放」按钮时，用第一组第一条兜底

`DetailRoute.playable` 只认 `detail.summary.playUrl` 与 `item.playUrl`（`docs/04 §7.4.2` 的"详情优先、列表兜底"）。
示例短剧源两个都拿不到——首集地址要 POST 才知道，详情响应里没有——于是详情页有选集格子、
却没有那个主按钮。用户要么点格子，要么以为"这源不能播"。

建议的兜底是**纯 UI 改动，不加配置字段**：

```kotlin
val playable = remember(detail, item) {
    val fromDetail = detail?.summary?.playUrl?.takeIf { it.isNotBlank() }
    val fromItem = item.playUrl?.takeIf { it.isNotBlank() }
    when {
        fromDetail != null -> detail?.summary
        fromItem != null -> item
        // 有分组就一定有能播的地址：拿第一组第一条当「播放」入口
        !detail?.trackGroups.isNullOrEmpty() -> item
        else -> null                                  // 纯图文源仍然不出现点不动的按钮
    }
}
// 起播时：detail.playUrl 为空则走 PlayTarget(item, groups, 0, 0)
```

原有两级判定不变，只是**再加一级**，且只在"有分组"时生效。

#### (3) 逐集一次请求在长剧上是纯等待（可选优化，暂时不做）

某部 42 集的剧 → 42 次 POST（`concurrency=4` 约 5~8 秒），第二次进详情才靠缓存兜住。
站点其实有批量接口 `POST /api/media/playback/previews {"ids":[…最多 20 个…]}`，一次回 20 条的 m3u8。

真要优化就加 `episodes.batch`（`request` + `idsPath` + `urlPath`），批量优先、失败回落逐条。
现在不做，理由：那是**第三级取数通路**，而 v1 的两条通路（`episodes` / `tracks`）已经能表达这份数据；
把"批量的形状"提前写进 Schema，等于让每个配置作者多学一种写法去换几秒。

### 5.2.9 HTML 图集：`tracks` 为什么抽不出来（图集实测，2026-11-16）

`samples/` 里的图集示例配置的列表侧完全跑得通（4 个栏目分别 25 / 57 / 50 / 100 条，`skipped=0`），
但详情页**只有元信息、没有图集网格**。这不是配置写漏了，是两条分组通路都不接受 HTML 源：

| 通路 | 需要什么 | HTML 详情页给的是什么 |
|---|---|---|
| `episodes` | `ids` 是 **JSONPath**，一条 id 一次子项请求 | 页面里只有 `<a href="/s/<hash>/<id>-<page>">`，没有 JSON 文档可求值 |
| `tracks`（`array`） | `from` 是 **JSONPath**，指向数组 | 同上，`Payload.Text` 上没有 JSON 树 |
| `tracks`（`delimited`） | 一个**字符串**里塞着 `$$$`/`#`/`$` 分隔条 | HTML 里没有这种串 |

再叠一层实测：列表页的缩略图**是雪碧图**——
`<div style="width:169px;height:300px;background:transparent url(https://.../4331869-0.webp) -200px 0 no-repeat">`
同一个 sprite 靠 `background-position` 切出每一页。把 `url(...)` 当"第 N 页的图"取，会得到 N 张一模一样的整片雪碧图。
真正的图在 `/s/<hash>/<id>-<n>` 页的 `#img`（`<img id="img" src="…">`），必须**二段请求**。

要支持这类源，两个候选（按推荐度）：

**A. `episodes` 支持 HTML 的 id 表（推荐）** —— 与示例视频源那条通路同构，只是"id 表"来自正则而不是 JSONPath：

```jsonc
"episodes": {
  "idsSplit": "<a href=\"https://gallery.example.org/s/[0-9a-f]+/(\\d+-\\d+)\">",  // 新增：正则切 id（group 即 id）
  "item": {
    "request": { "method": "GET", "url": "{{baseUrl}}/s/{{?}}/{{episode}}/" },  // 需要 {{episode}} 之外再带 hash
    "fields": { "title": …, "playUrl": { "kind": "regex", "pattern": "<img id=\"img\" src=\"([^\"]+)\"" } }
  }
}
```

好处：并发、单条失败跳过、缓存 TTL 全部复用现成实现；坏处：`/s/` 链接里 hash 与 `<id>-<page>` 是两段，`{{episode}}` 只带得动一个，
所以 id 表要给 `hash/id-page` 这种复合 id（和 图集站的 `/g/id/token/` 是同一手法：让 `{{}}` 原样替换、不编码）。

**B. `tracks` 增加 `mode: "html"`** —— `listSplit` + `fields{title,url,thumb}`，纯本地切分、零请求。
代价：`Track.url` 只能给 `/s/` **页面**地址，图片查看器拿到的是 HTML 不是图片，仍要二段解析；
而且雪碧图问题得靠 `background-position` 反推（配置表达不了）。所以只适合"每页一张独立 `<img>`"的站点。

在那两个能力落地之前，本样本的详情页就停在元信息（标题/评分/页数/标签/收藏数），**这是已验证的预期行为**，
不是"抽取失败"——`detail()` 里 `id`+`title` 齐了就返回 `MediaDetail`，`trackGroups` 为空而已。

### 5.3 并发与去重

同一 `(resourceName, paramsHash)` 的**并发**请求需要合并（避免快速切 Tab 打出 3 个相同请求）：

```kotlin
class InFlightGate {
    private val inflight = mutableMapOf<String, Deferred<*>>()
    suspend fun <T> run(key: String, block: suspend () -> T): T {
        inflight[key]?.let { @Suppress("UNCHECKED_CAST") return it.await() as T }
        val d = scope.async { block() }
        inflight[key] = d
        try { return d.await() } finally { inflight.remove(key) }
    }
}
```

**串行**判定：翻页请求必须串行（否则第 3 页可能先于第 2 页返回导致列表错位）。用 `Mutex` 保护每个 Tab 的分页。

### 5.4 缓存分层

| 层 | 位置 | 命中 | TTL | 失效 |
|---|---|---|---|---|
| L1 内存 | `LruCache<String, Any>`（32 项） | 同会话内切 Tab 返回 | 5 min | 下拉刷新主动清 |
| L2 磁盘 | HTTP `Cache-Control`（OkHttp 磁盘缓存 50MB） | 冷启动后再次访问 | 由服务端头决定 | 手动清缓存 |
| L3 离线包 | 可选（v2） | 无网时展示 | 用户导入 | — |

### 5.5 超时与重试：配置只能往小改（系统上限）

`runtime.timeoutMs` / `runtime.retry` 是**站点配置里的数字**，一份写错的配置（`timeoutMs: 0`、`retry: 99`）
能把界面卡死或打出几十次请求。所以这三个量按"默认 + 上限"两段管，**上限写死在 `core:source/HttpFetcher.kt`**：

| 常量 | 值 | 含义 |
|---|---|---|
| `DEFAULT_TIMEOUT_MS` | 15 000 | 配置没写时的单次请求超时 |
| `MAX_TIMEOUT_MS` | 30 000 | 单次请求超时**上限**（写 60s 也按 30s 走） |
| `DEFAULT_RETRY` | 2 | 配置没写时的重试次数（不含首次） |
| `MAX_RETRY` | 3 | 重试次数**上限** |
| `RETRY_DELAY_MS` | 3 000 | 两次重试的间隔，固定 3 秒，不做指数退避 |

`clampTimeout(ms)` 夹到 `1s..30s`（0/负数没意义），`clampRetry(n)` 夹到 `0..3`。
两个 clamp 在 `HttpFetcher` 构造里就执行，**上层拿不到"未夹过"的值**，也就不用在每处调用再判一次。

三个实现细节（都不是可选优化，是踩过的坑）：

1. **超时走 request 级 `timeout {}`，不重建 client**。`HttpClient` 是全 App 复用一个（切源不重建连接池），
   按源重建会丢掉连接池与代理配置。Ktor 的 `timeout { requestTimeoutMillis / connectTimeoutMillis /
   socketTimeoutMillis }` 可以逐请求改；`createHttpClient()` 里仍 `install(HttpTimeout)` 把三项都设成
   `MAX_TIMEOUT_MS` 兜底——某条请求万一漏配也不会无限挂着。
2. **重试只重"值得重试的"**。`SourceException` 新增 `retriable`：网络异常/超时（`E010`）为 `true`；
   `NET` 按 `status >= 500` 决定；**4xx 一律 false**（400/401/404 是确定的拒绝，重试只是把等待翻倍）。
   循环条件写成 `attempt >= retry || !e.retriable → throw`，首次 + 最多 3 次重发。
3. **重试是 fetcher 的事，不是管线的事**。首页与详情两条路走同一个 `HttpFetcher`，
   于是"详情里能跑通"和"首页能跑通"用的是同一套超时/重试，不会出现两套行为。

`SourcePipeline` 不参与重试决策，`UmpSession.of()` 只是把配置值传进去：

```kotlin
fetcher = HttpFetcher(client, timeoutMs = schema.config.runtime.timeoutMs, retry = schema.config.runtime.retry)
```

单测 `core/source/.../HttpPolicyTest.kt`（5 例全绿，`runTest` 的虚拟时间会把 3 秒间隔直接跳过，整套 0.24s）：

| 用例 | 断言 |
|---|---|
| `timeoutIsClampedToRange` | 0 / -5 → 1s；15s 原样；60s → 30s |
| `retryIsClampedToRange` | -1 → 0；2 原样；99 → 3 |
| `serverErrorIsRetriedUntilSuccess` | 前两次 500、第三次 200 → 成功，共发 3 次（retry=2） |
| `clientErrorIsNotRetried` | 404 → 立即抛 `NET`，只发 1 次（retry=3 也不重试） |
| `networkFailureRetriesThenGivesUp` | 引擎持续抛异常 → 抛 `E010`，共发 4 次（首次 + 3 次重发） |

验证边界（2026-11-15）：上限、clamp 与重试次数都由上面 5 例单测钉住（含 4xx 不重试）；
真机（`emulator-5554`）只验证了**正常路径没被拖慢**——首页正常出数、进详情正常、切源后仍能刷新。
**没有**在设备上人为制造"30 秒超时"或"连续 500"的场景（要改站点配置或起一个坏服务器，回归成本高），
这条留给真有源超时反馈时再补测；在此之前，"上限生效"的依据是单测而不是真机观察。

### 6.3 数据加载与 UI 解耦

渲染器**不发起网络请求**。它只接收 `UiState`：

```kotlin
sealed interface FeedUiState {
    data object Loading : FeedUiState
    data class Error(val msg: String, val canRetry: Boolean) : FeedUiState
    data class Ready(val items: List<MediaSummary>, val hasMore: Boolean, val skipped: Int) : FeedUiState

```

ViewModel 负责 `state = source.loadFeed(...)`，渲染器负责"把 items 画出来"。
这样"配置换了、布局换了"不影响数据层；"资源换了、接口换了"也不影响渲染层。

### 6.4 列表性能要点

```kotlin
LazyVerticalGrid(columns = GridCells.Fixed(node.layout.columns)) {
    items(items, key = { it.id }) { item ->   // ★ key 必须稳定，否则滚动时重组抖动
        PosterCard(item, spec = node.card)
    }
}
```

四条硬规则：

1. **`key` 用 `item.id`**，不用 index —— 翻页追加时避免整表重组。
2. **卡片内不 `remember` 派生状态**，只在 item 变化时重建（item 是不可变 data class）。
3. **图片走 Coil**，`placeholder` 用低分辨率模糊图，避免空白跳动。
4. **分页预取**：`LazyGridState` 的 `lastVisibleIndex > total - 4` 时触发 `loadMore()`，由 `derivedStateOf` 计算，避免每帧判断。

**封面加载的边界（2026-11-15 实测 → 2026-11-16 已解决，口径已改写）**：`AsyncImage` 解不出图时**静默留底色**、不崩、不影响标题与角标。
实测 `示例短剧源` 源（`/api/home/*` 的 cover 是相对路径 + `imageBase=https://示例图片域`）：
该 CDN 对这些路径返回 `200` + `Content-Type: binary/octet-stream` + 固定 270,080 字节，
首字节是 `09 3d e3 b1 …`，不是 JPEG /PNG /WebP 任一魔数；
带不带 `Referer` / `User-Agent` / `Accept: image/*` 返回**完全相同的字节**——不是防盗链，是**站点把封面以 AES 密文存放**。
> 早先这里写的是"站点侧资源本身不可解码、App 不改"——**该结论已被推翻**：站点有自己的 worker 先解密再塞 `<img>`，
> 用 `runtime.imageDecrypt`（`docs/03 §3.2`）在客户端解一遍即可正常出图。2026-11-16 已落地并实测：
> 示例短剧源首页 6 张封面、详情页大海报全部正常显示。

实现要点（细节见 `render/…/ImageDecrypt.kt` 的 KDOC）：

| 要点 | 原因 |
|---|---|
| 图片调用统一走 `UmpAsyncImage`，不直接调 `AsyncImage` | 只有一处判定"这个源要不要解密"，9 个调用点行为一致；源没声明规则时退化成原生 `AsyncImage` |
| **自己取字节 → 解密 → 明文交 Coil**，不走 Coil 的 `Fetcher` | 实测两遍：components 里加工厂、`fetcherFactory(...)` 请求级注册，密文 URL 都被原生 `NetworkFetcher` 抢先接走（自定义工厂 `create` 一次未被调用） |
| 解密产物校验含 JPEG 的 `FF D8 FF`，输入嗅探**不含** | 输入侧 2 字节太容易撞（会把密文当图）；产物侧已确知有密文，3 字节足够强。混用会把刚解出来的好图判死（表现为"下载成功但永远空块"） |
| 缓存明文（规则指纹 + 密文 URL 作键，24 条 LRU） | Coil 的磁盘缓存只认它自己下载的密文；不缓存明文，列表每滚一轮都要重下重解 |
| 解密失败静默留空位 | 与"字段失败不炸整页"同一思路；`W004` 提示尚未实现 |

同一台机器上的音乐示例源（`*.jpg`、`image/jpeg`）封面 20 张正常，说明图片通道与 Coil 配置没问题。

### 6.5 语义页面（`detail` / `player`）

这两类不做"配置排版"，因为它们有强交互（展开简介、切换线路、进度条）。
配置只提供**数据来源**与少量参数（`expandLines`、`columns`），组件结构由代码固定。

这是 01 §3 取舍一的直接体现：**能表达结构的地方用配置，需要精细交互的地方用代码**。

**详情页（`render/DetailView.kt` 的 `UmpDetail`，已落地）的三条硬规则**：

| 规则 | 为什么 |
|---|---|
| 标题 / 海报 / 年份一律取**用户点的那一条** `item`，不取详情接口返回的 summary | 详情接口给的是"该资源里的第一条"（示例配置的 feed 更是只有最新一条）；取返回值就会出现"点第 3 条、显示第 1 条标题" |
| 简介取详情返回的 `description`，行数由 `expandLines` 控制 | 只有简介必须走详情请求，其余字段列表页已经有了 |
| 详情请求失败只让**简介区**显示错误 + 重试，头部照常渲染 | 用户点进来的意图是"看这条内容"，不能因为一个字段拿不到就丢掉整页 |

播放地址在 M4 第一批之后**不再是纯文本**：`playUrl` 非空时 `UmpDetail` 渲染一个「播放」按钮（`onPlay` 由 `AppRoot` 注入，进播放页），地址仍以文本形式留在下方便于排查；`playUrl` 为空则不出现按钮（见 `docs/02 F4.6`）。`duration` 的格式化（`1:02:03` / `2:05`）在 `DetailView` 内部实现，不依赖平台。

### 6.6 主题映射：明暗看**配置的背景色**，`onBackground` 必须显式设

`ThemeSpec` 只有 5 个语义色槽位，`UmpTheme` 把它们映射成 Material3 的 `ColorScheme`。两条硬约束：

1. **`mode = SYSTEM` 时按 `background` 的亮度判定明暗**（`luminance() < 0.5f`），不看系统深色模式开关。
   背景色是配置写死的（默认 `#0F0F13`），跟着系统开关走必然割裂：模拟器是浅色模式时选 `lightColorScheme`，
   而背景仍被设成近黑。
2. **`onBackground` 必须一并设成 `onSurface`**。只设 `onSurface` 时，`Surface(background)` 的内容色会落回
   Material3 的默认 `onBackground`——浅色方案里那是 `#1C1B1F`（深色）。结果就是"黑底 + 深色字"，
   在模拟器上看起来像"空的 Activity"：文字其实都在，只是看不见。

顺带补齐 `onPrimary = background` 与 `surfaceVariant` / `onSurfaceVariant`，否则按钮文字、下拉菜单底色会各自跑偏
（黑底上的橙色按钮配深色字同样读不清）。

**这条教训的形态**不是"某处配错了"，而是"背景从配置来、前景从框架来"两套来源混用。
凡是这种组合，成对的前景色必须显式补齐。

### 7.4 当前实现（M3/M4 阶段的实际形态）

没有任何 ViewModel，也没有 NavHost。就一个 `AppRoot`，四个视图互斥、一条顶栏：

```kotlin
AppRoot(sources: List<SourceEntry>)          // 唯一挂载点；一个 HttpClient 用 remember 复用
 ├─ AppTopBar(...)                             // 一条顶栏，三种形态
 ├─ HomeRoute(session)                         // 列表页 → pipeline.list(feedKey, page, params)
 ├─ ContentRoute(session, item)                // 视频内容页（2026-11-20）：detail + 播放器合并
 ├─ DetailRoute(session, item)                 // 音频/图片详情页 → pipeline.detail(resourceKey, item.id, params)
 ├─ AudioRoute(session, target)                 // 音频播放页
 └─ SettingsScreen(current, sources, session)  // 设置页：切源 + 当前源信息 + 配置体检
```

状态（全在 `AppRoot` 里）：

| 状态 | 视图 | 顶栏 |
|---|---|---|
| `currentId`（数据源 id） | — | 决定用哪份 schema |
| `selected.kind == VIDEO` | 视频内容页（详情 + 播放器） | 左 **←** + 当前条目标题 |
| `selected.kind == AUDIO/IMAGE` | 详情 | 左 **←** + 当前条目标题 |
| `playing.kind == AUDIO` | 音频播放 | 左 **←** + 当前条目标题 |
| `settingsOpen = false` 且 `selected == null` | 首页 | 左 App 标识 · 右 **数据源下拉 + 齿轮** |
| `settingsOpen = true` | 设置 | 左 **←** + 「设置」 |

**返回顺序**：全屏 → 内容页/音频页 → 栏目 → 首页。视频不再同时持有 `selected + playing`：
点卡片只设 `selected`，`ContentRoute` 内部管理"预选集 / 是否起播 / 换集"，因此返回键只退一层。

**默认自动播放**：`ContentRoute` 的 `started` 初始 `false`，即使从历史带 `initialTarget` 也只预选不起播。
`autoPlay = SettingsKeys.PLAYER_AUTO_PLAY == "1"` 且详情返回后才选第一组第一条并置 `started = true`。
用户点封面播放键或选集时同样置 `true`。TV 不走 AppRoot，`openDetail(autoOpen = true)` 固定自动打开。

顶栏是**一个函数三种形态**（`AppTopBar`），下拉与齿轮只在首页出现（`onBack == null` 时）——
这是刻意的：详情页里再放个切源下拉，用户会以为切的是"当前这条视频的源"。

**为什么先不上 ViewModel / NavHost**：M3 的目的是验证"配置 → 渲染"这条链路能不能走通，
这时引入 ViewModel 只是把状态搬个家。等 M5（源管理、持久化）和 M4（播放进度、返回栈）
真的需要跨页共享状态时再搬，那时搬迁的代价才划算。

**源下拉的可见条数跟着屏幕走**（M5 收尾）：源一多，全量铺开会糊满整屏，也可能只露半个条目。
一项**单行 48dp**（Material 菜单项的最小触摸高度，再压低会把最后一项裁掉），
菜单限高取屏高的 55%（`LocalWindowInfo.current.containerSize`），再夹到 **4..8 项**，
超出的部分由 Material3 菜单自带的 `verticalScroll` 滚。
实测 720×1280（≈853dp 高）算出 9 → 夹到 8；6 个启用源时 `6 × 48 = 288dp`，菜单从 y≈145 到 y≈722，六项完整可见。

**下拉为什么从两行改单行（2026-11-15）**：原来每项是「源名 + `内置配置 · 在线请求`」两行，副标题对"选哪个源"没有信息量
（能出现在下拉里就一定是内置或导入 + 在线请求）。现在单行「源名（`weight(1f)`，超长省略）+ 版本号」：
版本号取配置的 `meta.version`，显示成 `v1.0.0`，右对齐、`labelSmall`、50% 透明度；**没写 `meta.version` 的源不显示**（不编造占位）。
`SourceEntry` 为此新增 `version`、删掉 `subtitle`（设置页单行化之后它已无处可显示），
`labelAndVersionOf()` 一次解析同时取 `meta.name` 与 `meta.version`——拆成两个函数会让启动时把每份配置编译两遍。

**选中标记从 ✓ 改成颜色（2026-11-16，M6.3）**：原来选中项前缀一个 `✓` 再拼进 `Text`，直接占掉两三个字的宽度，
长源名因此提前省略；而且"打勾"在中文语境里容易被读成"已看过 / 已收藏"。现在**一律不画勾**：当前源用它自己的
标识色（`sourceColors[current.id]`），其它项 `onSurface.copy(alpha = 0.55f)`。颜色来自 `SourcePalette`（见 §7.11），
设置页同一份 `sourceColors`，所以"首页顶栏那个色"和"设置里那一行那个色"永远是同一个。

`SourceEntry` 为此新增 `color`：`importEntryOf()` 里取 `meta.color`，没写就退到 `theme.primary`（若作者显式配过，
即不等于默认 `#FF6B35`），两者都没有就留 `null` 交给 `SourcePalette` 自动分配。

> 不要在 `DropdownMenu` 里再套 `LazyColumn`：M3 的菜单内容本身就是个带 `verticalScroll` 的 Column，
> 它用无界高度量子项，`LazyColumn` 会直接崩（"infinity maximum height"）。
> 限高加在 `DropdownMenu` 自己的 `modifier` 上，滚动交给它自带的那一个。

**返回栈怎么落到系统返回键**（M4 补齐，已装机验证）：

`AppRoot` 不直接持有平台 API，而是收一个槽位参数——**平台能力由壳层注入，feature 层不 import 平台**：

```kotlin
@Composable
fun AppRoot(
    sources: List<SourceEntry>,
    ...
    backDispatcher: @Composable (enabled: Boolean, action: () -> Unit) -> Unit = { _, _ -> },
)
```

- Android 壳：`backDispatcher = { enabled, action -> BackHandler(enabled = enabled) { action() } }`；
- 桌面壳：不注入（`cu`/窗口没有系统返回键），仍靠顶栏 ←。

`enabled` 直接取 `onBack != null`，所以"能返回"和"有返回键可点"是同一个判定，不会出现"顶栏有 ← 但系统返回退 App"的分叉。

> 踩过的坑：只接 `AppTopBar` 的 ← 而没接 `BackHandler` 时，设置页点 ← 能回首页，
> 但按系统返回键直接退到桌面——用户看到的是"我点返回，App 关了"。

### 7.4.1 栏目条（`ChannelBar`）与会话级缓存

**栏目条**：`PageSpec.channels` 非空时，列表页顶部渲染一条可横向滚动的 chips + 右端视图切换按钮。

**栏目条下面不再画页面标题**：`UmpPage` 原来会在内容区顶部渲染 `layout.title ?: page.title`
（示例视频源那行"会员视频示例源"大字就是它）。现在首页传 `showTitle = false` 把它关掉 ——
源名已经由顶栏右侧的下拉表达、栏目名已经在 chips 里，再顶一行属于重复信息，
省下来的是实打实的一段竖向空间（1280×720 窗口下多出约 40dp，首屏能多露半行海报）。
`UmpPage` 的 `showTitle` 默认仍是 `true`，留给以后没有顶栏提示的场景。

```kotlin
// HomeRoute
val active = channels.firstOrNull { it.id == selectedChannelId } ?: channels.firstOrNull()
val cacheKey = buildString {           // params 按键排序，保证同一栏目键稳定
    append(active?.feed ?: page.feed)
    active?.params?.toSortedMap()?.forEach { (k, v) -> append("|$k=$v") }
}
val layout = baseLayout.copy(type = viewMode)          // 视图切换只换 LayoutType
val card = active?.card ?: page.card                    // 栏目没声明 card 就继承页面级
```

三条落点：

| 设计点 | 做法 | 理由 |
|---|---|---|
| 栏目是取数入口 | 切栏目 = 换 `feed` + `params`，布局沿用页面级 | 不引入第二套布局体系（03 §9.5） |
| 视图与数据正交 | `viewModes` 只换 `LayoutSpec.type` | 换视图不该重新发请求 |
| 缓存键含参数 | `feed\|k=v&…`，参数按键排序 | 同一 feed 不同 `page`/`category` 不能撞键 |

**会话级缓存**：缓存挂在 `UmpSession` 上，不是全局单例。

```kotlin
class UmpSession(val schema: CompiledSchema, val pipeline: SourcePipeline, val source: SourceEntry) {
    private val feedCache = mutableMapOf<String, PagedResult<MediaSummary>>()
    fun cached(key: String): PagedResult<MediaSummary>? = feedCache[key]       // 命中就不再发请求
    fun remember(key: String, value: PagedResult<MediaSummary>) { feedCache[key] = value }
}
```

**分页状态就藏在这个 `PagedResult` 里**（`items` + `page` + `hasMore` + `skipped`），所以"每个栏目能不能记住自己翻到第几页"取决于两处有没有把它当回事：

| 时机 | 正确做法 | 曾经的做法（bug） | 现象 |
|---|---|---|---|
| 缓存命中 | `page = hit.page` | 写死 `page = 1` | 缓存里已合并到第 3 页，再滚动会重请求第 2 页并**重复追加**同一批条目 |
| 滚动加载成功 | `remember(key, 合并后的 PagedResult)` | 只改 UI state，不回写缓存 | 切到别的栏目再切回来，**翻页进度归零**，从第 1 页重来 |

两个坑的共同原因是：缓存最初只用来"省一次首屏请求"，没考虑它会承载翻页进度。现在缓存是**每栏目一份完整列表快照**，键仍是 `feed|params`（不含 page —— 页不是维度，是进度）。

为什么这样就"只在本次打开 App 内有效"：

- `AppRoot` 用 `remember(current, client)` 建 session → **切源即重建 session**，缓存随之丢弃；
- 进程退出，内存对象自然消失，**不落盘、不做过期淘汰**；
- 没有"后台刷新污染缓存"的路径：只有用户主动点栏目时才写缓存。

> 泛型坑（编译期踩过一次）：`mutableMapOf<String, PagedResult>()` 会报 `One type argument expected` /
> `Cannot infer type`。跨模块公开类型的集合**必须在声明处写实参**：`mutableMapOf<String, PagedResult<MediaSummary>>()`。

**校验落点（Schema 与实现必须同时改）**

`channels` / `viewModes` 不只是渲染层的约定，写错了要有可读报错，所以实现里两处（Kotlin 校验器 + Python 校验器）同时校验，文档这边是同一份口径：

| 情形 | 报错 | 在哪 |
|---|---|---|
| `channels[i].id` 为空 / 页内重复 | `E002` | `ConfigValidator.validatePages` + `tools/validate_config.py` |
| `channels[i].feed` 不在 `resources.feeds` | `E005` | 同上 |
| `channels[i].layout.type == detail` | `E003` | 同上 |
| `channels` 与 `children` 同时出现 | `E003` | 同上 |
| `viewModes` 含 `detail` | `E003` | 同上 |

`channels` 与 `children` 互斥是**语义级**约束：`channels` 切的是"同一套布局下的数据"，
`children` 切的是布局本身。两者同写会让用户看到"切了栏目、布局也跟着换"，无法预期，所以直接判错而不是猜一个。
`channels` 与 `children` 互斥这条是**后来才补齐的**：文档先写了规则，实现里没校验，等于"文档承诺了但代码不管"。
现在两边都补了，并各自验证过一次：

| 验证 | 做法 | 结果 |
|---|---|---|
| Kotlin | `ConfigValidatorChannelTest` 5 例（互斥 / id 重复 / feed 不存在 / viewModes 含 detail / 合法无错） | 5 例全过，0 skip（`core/config/build/test-results/jvmTest`） |
| Python | 拿 `samples/` 里的会员视频示例配置 副本手工塞一个 `children`，跑 `tools/validate_config.py` | 如期报 `[E003] pages[0].channels: channels 与 children 互斥…` |

Kotlin 校验器与 Python 校验器互为交叉验证——只改一边，`samples/*.json` 的 PASS/FAIL 就会出现分歧。

### 7.4.2 详情页"播放"按钮的判定（`playUrl` 可能晚于列表才出现）

详情页按钮的显隐不能只看**列表条目**的 `playUrl`：

```kotlin
// 错：示例视频源频道页列表条目只有一个 cid，直链要等详情解析完才有 → 按钮永远不出现
onPlay = if (item.playUrl.isNullOrBlank()) null else ...

// 对：先看详情结果，再看列表条目
val playable = detail?.summary?.playUrl?.takeIf { it.isNotBlank() }?.let { detail!!.summary }
    ?: item.takeIf { !it.playUrl.isNullOrBlank() }
```

这条差异的来源是**两种源的取数形状不同**：

| 源形态 | 列表里的 `playUrl` | 详情里的 `playUrl` |
|---|---|---|
| 示例视频源（Atom） | 有（watch 页链接） | 有 |
| 示例视频源频道页（SSR focusList） | **没有**，只有专辑 `专辑 id` | 有（`详情接口（参数含专辑 id）` 拼出的直链） |

所以判定顺序是"详情优先、列表兜底"，两者都没有才不给按钮（纯图文源不显示点不动的按钮）。


### 7.5 数据源（`SourceEntry`）只是一个数据对象

```kotlin
data class SourceEntry(val id: String, val label: String, val subtitle: String, val json: String)
```

四条设计约定：

| 约定 | 理由 |
|---|---|
| 只装**原始 JSON**，不装编译产物 | 选中之后才 `ConfigCompiler.loadAndCompile`。一份坏配置只会让那一屏出错误面板，不会在选择器里就崩 |
| `label` 取配置的 `meta.name`，取不到用文件名兜底（`labelOf()`） | 下拉里要显示"人能看懂的名字"，不能显示 `示例视频源` 这种 id |
| `subtitle` 显示 `baseUrl + 取数方式`（如 `www.示例视频源.com · 在线请求`） | 用户对"到底连了哪个站、是真是假"极其敏感，这行字就是回答。**设置页自 2026-11-15 起不再渲染它**（源项单行化，见 §7.5.2）；下拉菜单仍用它区分源 |
| 装配在 `UmpSession.of(entry, client)`：编译 + `SourcePipeline(schema, HttpFetcher(client))`，**一个 `HttpClient` 复用** | 切源不重建连接池 |

谁能提供数据源（**2026-11-16 起两端口径统一：都只读"用户导入"**）：

| 端 | 取法 | 实现 |
|---|---|---|
| 桌面 | `~/.vi-ump/sources/*.json` | `DevSourceLoader.loadAll()`（名字沿用，内容已改成只读用户目录），顺带在原始 JSON 上抠出 `proxyBypass` 交给 `ProxySupport` |
| Android | `filesDir/sources/*.json` | `UserSourceLoader.loadAll()`（取代 `AssetSourceLoader`）|

> **不再有"预置源"**：APK 里不再打包 `assets/sources`（仓库 `samples` 不再挂成 assets），jar 也不扫仓库目录。
> 理由是"站点配置的唯一真相是用户导入的那一份"——APK 里带一份就成了两个真相，站点改版后
> 用户看到的还是旧的、而他又不知道 App 里有内置副本。代价是全新安装没有可用源，由 M5.10 的空态兜底
> （`catalog.isEmpty()` → 直接进设置页并提示先导入一份）。
>
> 踩过的空态：Android 的 `MainActivity` 早先调 `AppRoot()` **没传 `sources`**，装机后就是一个"几乎全黑的空 Activity"——
> 顶栏下面只有一行"还没有数据源"。同一轮还叠了 §6.6 的黑底黑字，两件事一起才让人以为"App 什么都没渲染"。

### 7.5.1 用户导入源与删除（M5，双端已落地）

`SourceEntry` 带一个 `builtin: Boolean = true`（历史字段）：M5.10 之后列表里**已经不存在内置源**，
这个标记只剩兼容用途（老代码/测试构造 entry 时用），实际判断"能不能删"的那条路已改成"只要不是当前源就能删"。

```
设置页「导入」（文件）/「粘贴」（文本）/「URL」（拉取）
  → 文件：壳层选文件（Android SAF OpenDocument / 桌面 AWT FileDialog）
  → 粘贴：设置页内对话框，`SourceActions.onImportText(text)` 返回 null=成功 / 非 null=原因留在对话框
  → URL：`SourceActions.onImportUrl(url)`（挂起），壳层 IO 线程 `fetchConfigText()` 拉文本，
    拉取中按钮禁用；协议白名单 + HTTP 状态检查 + 空内容检查在 feature 层统一做
  → importEntryOf(text)（feature 层）：ConfigCompiler 校验，不过就抛"前两条问题"；
    解析期异常只取首行原因（kotlinx 原始消息带开发者建议，整段透传会撑满对话框）
  → UserSourceStore.save(meta.id, text)（core:storage，expect/actual）
  → 壳层重新 loadAll()，sources 是 State，就地刷新
```

| 决策 | 理由 |
|---|---|
| 校验放 feature 层，不放壳层 | `ConfigCompiler` 只有 feature 该碰；壳层只做"拿文本 → 调函数 → 落盘 → 刷新" |
| 存储放 `core:storage`，不放 feature | feature:main 只有 commonMain，没有 androidMain；core:storage 本来就有三源码集与 Context 注入 |
| 文件名 = `sourceFileName(meta.id)`（非法字符转 `_`） | meta.id 是配置作者写的，可能带斜杠/空格/中文 |
| 同 id 覆盖（含覆盖已导入的同名源） | "重导一份改过的配置"是最常见的操作；文件名即 id，覆盖才符合直觉 |
| `sources` 在壳层是 `mutableStateOf` | 导入/删除必须就地可见，不能"重启 App 才看到新源" |
| 删除走**左滑**、且弹窗带源名 | 删除按钮挤在行尾会让源行变宽；右滑/左滑是移动端删除的通行手势。删掉使用中的源会把当前页抽空，所以当前源不给删；破坏性动作必须有一次明确确认（滑动阈值 112dp，见 §7.5.2） |

实测（emulator-5554）：导入 `音乐示例源-rock.json` → 列表末尾"摇滚音频（导入配置）"→ 切源出 20 张封面；
删除另一份导入配置 → 确认弹窗 → 列表消失、`run-as com.vi.ump ls files/sources/` 只剩目标文件。
粘贴通道：注入 3011 字节配置 → 列表末尾"PasteDemo"、`paste-demo.json` 落盘；非法 JSON → 对话框红字 `[E002]` 不关闭。
（adb 注入长文本要分段：`input text` 一次塞 3KB 会被系统 kill；按 150 字节一段循环注入即可，非 ASCII 先 `ensure_ascii` 转义。）

**URL 拉取的两个网络坑（都已修，勿回退）**：

1. **系统代理会吃掉内网地址**：模拟器/桌面带着 Clash 这类系统代理时，`http://10.0.2.2:8765/...`
   也被送进代理隧道，代理够不到宿主机就回 **502**。URL 导入的 client 单独配 `LocalFirstProxySelector`：
   `localhost / 127.x / 10.x / 192.168.x / 172.16–31.x / ::1` 直连，其余仍走系统默认代理。
   这只影响导入用的 client，站点请求的 client 与 `runtime.proxyBypass` 机制不变。
2. **模拟器直连宿主机端口可能被拦**：`10.0.2.2:8765` 连接超时（宿主机防火墙）。
   联调用 `adb reverse tcp:8765 tcp:8765`，App 改访问 `http://127.0.0.1:8765/...`，走 adb 通道即通。
   明文放行只加在 `10.0.2.2 / 127.0.0.1 / localhost` 三个开发地址上（`network_security_config.xml`），
   没有全局放开 cleartext。

### 7.5.2d 删除改成左滑（2026-11-16）

```
dragX（mutableStateOf）累积水平位移
  → offset = dragX.coerceIn(-maxSwipe, 0)          // 只往左拉
  → 松手：|dragX| >= 112dp → 弹确认框（带源名）；否则 dragX 归零回弹
  → 确认：UserSourceStore.delete(id) → 刷新 sources
```

| 决策 | 理由 |
|---|---|
| `dragX` 用 `mutableStateOf`，**不要换成 `Animatable.snapTo`** | 第一版用 `Animatable`：每次拖动都 `snapTo` 起一个协程，位移追不上手势；松手时读到的仍是 0，被判"未达标"直接回弹，表现是**怎么滑都删不掉**。换成普通 state 后逐帧跟随 |
| 阈值 112dp | 太小会误触（列表纵向滚动一开始就带水平抖动），太大滑不动。112dp ≈ 行高的 2.5 倍，720×1280 上实测刚好 |
| 滑过阈值就整行变红、文案变「删除」 | 手势要有"将要发生什么"的预览 |
| 确认框仍然保留 | 滑动本身不能当确认（误滑很常见）；破坏性动作必须有一次明确确认 |
| 当前源不给删 | 删掉会把当前页抽空（沿用旧约束） |

实测（`build/ui52_swipe2.png`）：左滑 `音乐示例源-rock` → 露出红色「删除」→ 松手弹确认 → 确认后列表消失、`files/sources/` 只剩目标文件；取消则回弹、不误删。

### 7.5.2b 设置页「当前数据源」只留事实行

「名称 / 标识 / 站点 / 版本 / 资源 / 页面 / 导出」之外，原来还有一行

### 7.5.3 导出与脱敏（M5.5，已落地）

```
设置页「导出配置（已脱敏）」
  → maskForExport(current.json)（core/source/ExportMasking.kt）
  → SourceActions.onExport(json, "vi-ump-<id>.json")
  → Android：SAF CreateDocument("application/json")；待写文本先存 pendingExport，uri 回来再写
  → 桌面：AWT FileDialog(SAVE) + writeText(UTF-8)
  → 结果回显一句：已导出（已脱敏）：<文件名> / 导出失败：<原因>
```

脱敏只做**高置信度替换**，因为导出的文件必须还能被"导入"通道吃回去：

| 规则 | 例子 |
|---|---|
| 键名命中敏感词 → 值整段换 `<已脱敏>` | `"Authorization": "<已脱敏>"` |
| 字符串里的 Bearer 令牌 | `"note": "Bearer <已脱敏>"`（只留前缀） |
| `phone/mobile/tel/contact/msisdn` 键的 11 位号码 | `"phone": "138****5678"` |

**键名匹配用切词，不是 `contains`**（这是实测踩出来的坑）：早前 `isSensitiveKey =
lowercase().contains(词)` 把 `author` 判成了 `auth`，实测导出 `"author": "vi-ump-samples"`
变成 `"author": "<已脱敏>"`——作者信息被抹掉，而文件本身仍能通过校验，属于"静默改坏"。现在：

- `keySegments(key)` 按分隔符（`_` `-` `.` 空格）与驼峰切词：`Authorization` → `[authorization]`、
  `access_token` → `[access, token]`、`X-Api-Key` → `[x, api, key]`、`author` → `[author]`；
- 命中 = 任一片段 ∈ 敏感词表（token/cookie/authorization/auth/secret/password/passwd/signature/credential/sessionid）
  或整串以连写敏感词结尾（`apikey`/`accesskey`/`accesstoken`/`sessionid`…）；
- 于是 `author`、`authorName`、`design`、`sign`、`signCount` 都不再误伤，
  由 `core/source/commonTest/ExportMaskingTest.kt` 守住（7 例，含 `author` 回归）。

**手机号只认号码键**：11 位数字也可能是 `id`，所以打码限定在 `phone` 类键的字符串值上，
数字字面量与长 id 中的数字段不动。

替换只发生在**字符串值内部**，JSON 结构与键名一字不动 → 脱敏文件可回环导入（验收口径）。

实测（模拟器 `emulator-5554`）：

1. 源 `示例短剧源` 导出 → `Download/vi-ump-示例短剧源.json`（15,783 字节），
   `validate_config.py` PASS；首版把 `author` 误脱成 `<已脱敏>`（`contains("auth")` 的锅），
   修正键名切词后 `author` 原样保留。
2. 造 `mask-demo`（在 `runtime.headers` 里塞 `Authorization` / `X-Api-Key` / 一条 `X-Note: Bearer …`）
   → URL 导入 → 切源 → 导出 `Download/vi-ump-mask-demo.json`，读回确认：
   `"author": "vi-ump-samples"` 保留、`"Authorization": "<已脱敏>"`、`"X-Api-Key": "<已脱敏>"`、
   `"X-Note": "Bearer <已脱敏>"`，7 个顶层键一个不少。
3. **回环**：拿上面这个导出文件走"导入"通道（SAF 文件选择器）→ 提示「已导入「MaskDemo」（mask-demo），
   在数据源列表末尾」→ 设备上 `files/sources/mask-demo.json` 被同 id 覆盖为脱敏版（头里的 token 已是占位符）。
   这条链路走通，才算 M5.5 验收。/

### 7.6 详情页的参数回退（一条容易漏的规则）

配置里 `params` 是"页面级参数"。列表页声明 `{"channelId": "UC_..."}`，请求 URL 里写 `{{p.channelId}}`。
但详情页通常**什么都不声明**——因为它只是"取同一份数据的另一条"，参数属于整个站点。

于是定一条规则：**详情页 `params` 为空时，复用第一个非详情页的 `params`**。

```kotlin
val params = page?.params?.takeIf { it.isNotEmpty() }
    ?: schema.pages.firstOrNull { it.layout.type != LayoutType.DETAIL }?.params.orEmpty()
```

- 详情页显式声明了就用它自己的（保留覆盖能力，不同站点的详情可能真要额外参数）；
- 没声明则回退，避免 `{{p.channelId}}` 渲染成空串、请求打到 `channel_id=` 拿 404。

这条规则是**运行期兜底**，不是校验器的职责：校验器仍允许详情页不写 params（写了才校验引用是否存在于资源里）。

### 7.7 播放进度记忆（`core:storage` 的 `ProgressStore`）

M4.7 只要求一件事：**同一条内容再点进来，从上次看的地方继续**。
所以这一层只落一个 `key -> positionMs`，不碰"看过什么"（历史/收藏在 M6，那时才换 SQLDelight，见 §10）。

```kotlin
interface ProgressStore {
    fun position(key: String): Long?          // 没记录返回 null，不是 0
    fun save(key: String, positionMs: Long)
    fun clear(key: String)
}
expect fun createProgressStore(): ProgressStore

fun progressKey(sourceId: String, itemId: String, episode: Int = 0): String = "$src|$id|$ep"
```

**键为什么是"源 + 条目 + 集号"三段**：

| 段 | 不带的后果 |
|---|---|
| 源 | 不同源的 id 很可能撞（都是数字 id），撞了就是"看了示例视频源第 3 集，却从 示例视频源的进度续播" |
| 条目 | 显然 |
| 集号 | 视频的进度语义是 `(episodeIndex, positionMs)` 而不是单条 id 一个位置；不分集，切集就是接着上一集的时间点 |

**两端实现都挑"零依赖"路径**：

| 端 | 落点 | 为什么 |
|---|---|---|
| Android | `SharedPreferences("ump_progress")` + `apply()` | 进度是"丢了也无所谓"的数据，异步落盘避免主线程 IO；用 `AndroidStorageHost.install(this)` 注入 `applicationContext`（`createProgressStore()` 不带参数） |
| 桌面 | `Preferences.userRoot().node("com/vi/ump/progress")` | JDK 自带用户级键值存储，不用选路径、不会有文件占用 |
| 都失败 | `InMemoryProgressStore` | 存储不是关键路径：宁可"记不住"，不能"点开播放就崩" |

**路由层的四个写点**（`feature/main/PlayerRoute.kt`）：

```
进入：resumeMs = store.position(key) ?: 0  →  prepare(url, headers, kind, startMs = resumeMs)
播放中：LaunchedEffect(key) { while (true) { delay(5s); save } }   // 心跳，positionMs > 3s 才写
离开：DisposableEffect.onDispose { 先补写一次，再 facade.release() }  // 补上最后 5 秒
播完：status == ENDED → clear(key)                                  // 下次从头看
```

`resumeMs` **只读一次**（`remember(key)`）：若在播放中反复读，会读到当前位置，每次重组都把
`prepare(startMs=…)` 的入参往后推，表现为"画面自己往前跳"。

界面上不做额外弹窗，只在 meta 行加一句 `上次看到 00:36`（`UmpPlayer` 的 `resumedFromMs` 参数）——
续播这件事"看得出来就行"，弹层反而打断。

**实测**（`build/progress_probe.py`，模拟器）：播到 `00:36` → 返回详情 → 重新点「播放」→
`时长 03:25 · 就绪 · 上次看到 00:36`，进度条从 36 秒起，不是 0。

### 7.8 上次选中的数据源（跨进程记忆）

顶栏的数据源下拉，每次开 App 都回到第一条很烦。它和 §7.7 的进度语义不同：
**这是"用户的选择"，卸载才清**，不能随会话失效，所以不能挂在 `UmpSession` 上（那是会话级缓存的宿主）。

`core:storage` 的 `AppSettings`（`getString` / `putString`）两端都不需要新依赖：

| 端 | 落点 |
|---|---|
| Android | `SharedPreferences("ump_settings")` |
| 桌面 | `Preferences.userRoot().node("com/vi/ump/settings")` |
| 注入失败 | `InMemoryAppSettings`（同 §7.7 的兜底原则） |

键集中在 `SettingsKeys`（`SOURCE_ID = "source.lastId"`），避免字符串散落到各 feature。
`AppRoot` 启动时读、`selectSource` 时写。

**一条容易漏的兜底**：读到的 id 必须先用当前 `catalog` 校验一次——

```kotlin
settings.getString(SettingsKeys.SOURCE_ID)?.takeIf { id -> catalog.any { it.id == id } }
    ?: catalog.firstOrNull()?.id
```

否则用户换过配置（旧源被删）时会落进"当前源不存在"的分支，表现为开 App 一片空白。

**实测**：切到会员视频示例源 → `am force-stop` → 重开，顶栏仍是「会员视频示例源」（默认第一条与它不同，故能区分"记忆"与"默认"）。

### 7.9 选集：两级取数 + 按状态拆组（M4.4）

选集不是硬编码示例视频源逻辑，而是配置里的一段 `episodes` 规格（`docs/03 §5.5`），管线负责三级取数，渲染层只认 `TrackGroup`。

```
detail()  ──► buildEpisodeGroups(res, payload, vars)
                │
                ├─ ① id 表   : episodes.request（取 id 表那一步）→ root → ids 路径求值 → 展平 → distinct → take(maxItems)
                ├─ ② 子项    : ids.withIndex().chunked(concurrency) → async { fetchTrack(...) }.awaitAll()
                │              每条渲染 url（{{episode}} = 当前 id，{{id}} = 条目 id）→ fetch → strip → root → 抽 title/duration/playUrl
                └─ ③ 拆组    : 按 state 分成 选集（free/vip，按集号排序）/ 预告（trailer）/ 花絮（extra）
```

**为什么必须两级**：有些源把"有哪些集"和"每集是什么"拆在两个接口里，id 表那个还是 `POST`（要带一个自造 cookie，不带就报业务错误码），详情那个是 `GET`。详情接口 **不支持批量**——一次传多个 id 就整批报错，所以只能一个 id 一次请求。48 条按 `concurrency=6` 并发实测 1.5~2 秒，可接受。

**为什么要拆组**：`video_ids` 的顺序不等于集号。某剧 48 个 id 里，1~5 是正片 `_01`~`_05`，6~22 全是预告片（80~99 秒），23~39 才是正片 `_06`~`_22`，41~43 又是预告，44~48 是彩蛋（全部无 `播放凭证字段`，不可播）。不拆组就会出现两个"第6集"、用户无从分辨。

**状态标怎么来**（优先级从高到低）：

| 来源 | 判定 | state |
|---|---|---|
| `badges` 命中标题关键词 | 标题含"预告" / "彩蛋" | `trailer` / `extra` |
| `lockedPath`（`$.播放凭证字段`）取不到 | 没凭证 = 不可播 | `vip` + `lockedLabel` |
| 其余 | 有凭证 | `free` |

`state` 故意用字符串而不是枚举：站点口径会变（限免 / 会员 / 超前点播），多一种状态不该改代码，渲染层兜底配色。

**三个踩过的坑**

| 坑 | 现象 | 根因与修法 |
|---|---|---|
| 数组没展平 | 日志 `[ep] ids=0`，详情页选集整块消失 | `$.coverInfo.video_ids` 求值只回一个 `JsonArray`，按标量取 `as? JsonPrimitive` 全为 null。改成先 `flatMap { if (it is JsonArray) it.toList() else listOf(it) }` |
| 只调 extractor 不走变换链 | 选集每集都报 `[P2007] Source error` | CDN 返回的是 `http://203.0.113.10/cdn.example.com/…`，靠字段的 `rewrite` 去掉 IP 段。直接取 `extractor` 的原始值会保留 IP，Media3 起播即失败。改成 `raws.mapNotNull { TransformChain.apply(it, spec) }` |
| 进度串集 | 播第 3 集会把第 1 集的续播点覆盖 | 进度键原本只有 `源|条目`。选集后加集号：`progressKey(sourceId, itemId, episodeIndex)`，`AppRoot` 持 `playingEpisode` 并在点集时写入 |

**实测（Android 模拟器，示例视频源《示例剧集》）**：详情页显示 `选集 · 共 22 项`（第1集~第22集，全部 `免费`）、`预告 · 共 20 项`（预告6~25）、`花絮 · 共 5 项`（彩蛋1~5）。点「第1集」进播放页，标题 `剧名_01`、`时长 03:25 · 播放中`。

**能力边界（如实记账）**：`播放凭证字段` 只能判"可播/不可播"。示例视频源对未登录请求的 VIP 集照样返回 `播放凭证字段`，而 `coverInfo.downright`（免费集索引）实测会溢出——48 条数据里出现索引 48/57/61。所以"免费 vs 会员"目前**没有稳定字段**，只显示 预告 / 花絮 / 不可播 三类，其余按免费处理。要精确区分需要登录态 + `playright` 口径，属后续工作。

### 7.10 选集缓存：持久化 + 6 小时 TTL（M4.4 续）

选集是详情页里**唯一"重"的部分**：一级 id 表 1 次请求，二级每条一次 `详情接口`，
《示例剧集》48 条、`concurrency=6` 实测也要 1.5~2 秒。这个代价每次进详情页都要付一遍，
所以在 M4.4 之后补了一层缓存。

**为什么是持久化缓存，而不是复用首页那个会话缓存**

| 缓存 | 位置 | 生命周期 | 为什么 |
|---|---|---|---|
| 首页列表 `UmpSession.feedCache` | 进程内存 | 切源 / 退 App 即失效 | 用户明确要求"只在本次打开 App 时生效"；列表本来就有"看最新的"诉求 |
| **选集 `EpisodesCache`** | SharedPreferences / java.util.prefs | **6 小时 TTL**（写入时间戳判定） | 用户要求"和播放进度一样的持久化"；但"永远不失效"会把脏数据钉死，`vkey` 本身也只有几小时时效 |
| 播放进度 `ProgressStore` | 同上 | 卸载才清 | 用户的位置不能过期，"上次看到 02:58"三天后也要能续 |

三者都是"键值 + 平台注入"的形状，`core:storage` 里并列放着，不共用实现。
选集这一层是全仓库**唯一带 TTL 的持久化**：它不是"用户的选择/进度"，而是"站点数据的副本"，
副本就该有时效。

**存什么：渲染完的 `Track` 列表，不是原始响应**

原始响应（id 表 + 48 份 `详情接口`）还要再跑一遍变换链、拆组、排序、状态判定，
缓存它等于只省了网络、没省计算；而 `TrackGroup` 是渲染层的直接输入，
读出来就能交给 `TrackGrid`。代价是要为它定一个私有 JSON 格式，见 `EpisodeCacheCodec`。

```jsonc
// 存进去的形状（字段名刻意短：48 集约 3~5KB）
{"v":1,
 "g":[{"n":"选集","k":"video",
       "t":[{"i":1,"ti":"剧名_01","u":"http://…mp4","d":205000,"s":"free"}, …]}]
}
```

- `v`：格式版本。升级字段就改这个号，旧缓存自然解不出来，走重拉。
- `i/ti/u/d/s`：集号、标题、播放地址、时长、状态。`s` 缺省表示"没状态标"。
- 解码失败一律返回空列表（`getOrDefault(emptyList())`）：缓存坏了只影响命中，不影响功能。

**键与失效**

- 键 = `源|条目`（`episodesCacheKey`），不带集号 —— 缓存的是"整部剧的全部集"。
  带源的理由同 `progressKey`：两个站点的 id 形状不同但可能撞。
- **6 小时 TTL**（`EPISODES_CACHE_TTL_MS`）：写入时额外存一条 `源|条目#ts`（epoch 毫秒），
  读的时候 `now - ts > 6h` → 视为 miss，顺手把整条（正文 + 切片 + 片数 + ts）删掉重拉。
  - **没有 `#ts` 的一律算过期**（老版本写的缓存）。这是刻意的：否则存量数据永远不会过期，
    "加了 TTL"等于没加；代价只是升级后每部剧重拉一次（1~2 秒）。
  - `now - ts <= 0`（时钟被回拨）按"刚写入"处理，不删 —— 否则机器时间一改，全部缓存集体失效。
- 不再需要"改配置后人工清缓存"：改 `episodes` 抽取规则后，最多 6 小时脏数据自然消失。
  `EpisodeCacheCodec` 的 `v` 版本号仍然是**格式级**失效手段（字段结构变了必须升版）。
- **空结果不落盘**：取数失败（站点临时抽风）写进去会把上一次的好数据顶掉。

**TTL 是常量，但应该按源配置**（2026-11 补）：`EPISODES_CACHE_TTL_MS` 写死 6 小时，对"地址长期有效"的源是对的；
对"地址两小时就过期"的源（示例短剧源的 `streams.main` 带 `auth_key`）是错的——缓存命中反而**必然**播放失败，
而且失败现场在播放器（`P2007`），离"缓存旧了"这个真因很远。
`episodes.cacheTtlMs`（缺省 6h，`docs/03 §5.5`）的改法与落点见 `§5.2.8 (1)`。

**桌面端的 8K 限制**

`java.util.prefs` 在 Windows 上单值上限 8192 字符（注册表约束），48 集的 JSON 很容易超。
`PrefsEpisodesCache` 按 8000 字符切片存成 `key#0…key#n-1`，并用 `key#n` 记片数、`key#ts` 记时间戳；
读的时候拼回来。Android 的 SharedPreferences 没这个限制，直接整块存一个值 + 一个 `#ts` 值。

**实测**

| 场景 | 首次进详情 | 第二次进详情 | 缓存文件 |
|---|---|---|---|
| 《示例剧集》48 条 | 11 秒才看到完整选集（含骨架等待） | **3 秒内选集已完整渲染** | `ump_episodes.xml` 37,236 字节 |

TTL 落地后的实测（桌面端，注册表为证）：

| 动作 | 观察 |
|---|---|
| 升级前存量缓存（`<sourceId>\|<entryKey>#0…#4` + `#n`，**无 `#ts`**） | 注册表 12 个值，无时间戳 |
| 升级后第一次进同一条详情 | 存量被判过期 → 重拉 → 写回 `…\|<条目 key>#ts = <epoch millis>`（距当时 31 秒） |
| 返回首页再进同一条详情 | 3~5 秒内 22 集全部出现（未过期，正常命中，没被误判） |

`pm clear` 之后回到默认源（模拟器连不上外网源）是预期行为：源选择本身也是持久化的，
清数据等于恢复默认。

### 7.11 源标识色（`SourcePalette`，M6.3）

多个源摆在下拉和设置列表里，只靠名字扫一眼分不出来，颜色是"这是哪个源"最快的线索。
但**颜色不能由客户端随意造**：作者在配置里写的颜色必须原样显示，两个源都写了同一个颜色时也要真的同色
（用户 2026-11-16 的口径）。所以分配分两步走，只有"没配的"才进入自动分配。

**优先级**（`importEntryOf()` 里就把前两级定下来，存进 `SourceEntry.color`）：

| 顺序 | 来源 | 说明 |
|---|---|---|
| 1 | `meta.color` | 显式指定，原样用 |
| 2 | `theme.primary` | 若作者显式配过（≠ 默认 `#FF6B35`）。等于默认说明没配，交下一步 |
| 3 | 自动分配 | `SourcePalette.assign()` |

第 2 级是刻意的兼容：老配置只有 `theme.primary`，没有 `meta.color`，它们也应该各有一个能区分的颜色，
而不是全落到默认橙上。这也让"只想换个主题色"的作者不必多写一个字段。

**自动分配的算法**（`object SourcePalette`）：

```kotlin
// 常量：MIN_HUE_DISTANCE = 40f、GOLDEN_ANGLE = 137.508f、AUTO_SATURATION = .62、AUTO_LIGHTNESS = .58
1. 先把显式色登记进 usedHues（灰度色 hueOf 返回 -1，跳过——它不与任何色相冲突）
2. 对每个没色的源：
   seed = (id.hashCode() as 无符号 32 位) % 360        // 同一个 id 永远从同一个色相出发
   hue  = (seed + k * 137.508°) % 360, k = 0,1,2…       // 黄金角试探：相邻两次天然差 137°
   取第一个与 usedHues 全部相差 ≥ 40° 的 hue（最多试 24 次），登记后再 hsl(hue) 造色
```

- **为什么按 id 落种子**：源列表顺序变了、删了一个源，其余源的颜色都不该跟着乱跳。加一个源只影响它自己
  （除非真的所有空位都被占了）。
- **为什么是黄金角而不是"按序号 × 360/n"**：后者要求知道总数，源一增一减就全体重算；
  黄金角的连续试探天然分散，且不需要全局信息。
- **40° 的理由**：低于这个差距，两个源在中亮中饱和下看起来是同一个颜色系（比如都偏橙），等于没配色。
  360/40 = 9 个互不相同的色相槽，对"用户导入源"这种规模足够。
- **灰度显式色不参与冲突判断**：白/灰/黑没有色相，把 -1 算进环形距离会把整圈都判成冲突。

**渲染口径**（`AppTopBar` + `SettingsScreen` 共用 `AppRoot` 里那一份 `sourceColors`）：

| 位置 | 已选择 | 未选中 / 停用 |
|---|---|---|
| 首页顶栏当前源名 | 该源颜色 | — |
| 下拉项 | 该源颜色，**不画 ✓** | `onSurface` 55% |
| 设置页源名 | 该源颜色 | 55% / 停用 45% |

`AppRoot` 里一次算全表：`remember(catalog) { SourcePalette.assign(catalog) }` —— "不与已有色相同"是全局约束，
必须整表一起算。生成是纯函数，同一份 catalog 得到同一份颜色，不会因重组而闪色。

**主题主色也跟着源**：`theme.primary` 仍是默认 `#FF6B35` 时，用该源色 `copy(primary = color.toHex())`；
作者显式配过就尊重作者。这样切源时按钮、选中态、输入框焦点色都跟着变——实测切到示例短剧源后
"最新"频道 pill 与重试按钮都变黄。

**测试**（`feature/main/src/commonTest/.../SourcePaletteTest.kt`，5 例）：6 个源两两色相差 ≥40° 且互不相同、
显式色不被覆盖、显式同色允许共用、非法 hex 降级为自动色、`parseHex`/`toHex` 往返。

### 7.12 搜索页（`SearchRoute` + `SearchController`，M6.3）

**入口**：首页顶栏 🔍 放在「源选择」下拉**左侧**（`AppTopBar` 的 `onSearch` 参数，`current != null` 时才画）。
是否出现由 `AppRoot` 算：`canSearch = flags.enableSearch && schema.search.isNotEmpty()`。
**两个条件缺一不可**——只写 `enableSearch=true` 却没配 `resources.search` 的源，按钮不出现，
否则用户点进去看到的是一屏"这个源没有配置搜索"。切源时 `LaunchedEffect(current?.id) { searchOpen = false }`。

**为什么状态放在 `AppRoot` 而不是页面里**（这是本轮修掉的一个缺陷）：第一版 `SearchRoute` 自己 `remember` 查询词与结果，
从搜索结果点进详情再返回，`SearchRoute` 被重新组合、`remember` 丢值 → **关键词与列表全空**，用户以为"搜索坏了"。
现在 `SearchController` 由 `AppRoot` 持有：

```kotlin
val searchController = remember(session) { session?.let { SearchController(it) } }
```

`session` 是切源的边界，所以控制器跟着源重建；页面进出不再影响它。`onBack` 顺序里 `searchOpen` 排在详情之后：

```kotlin
viewing → playing → settingsOpen → selected(详情) → searchOpen
```

**控制器里有什么**（`SearchController`）：

| 成员 | 作用 |
|---|---|
| `searchKey` / `pageSpec` | `schema.search.keys.firstOrNull()`；页面布局取配置里 `layout.type == SEARCH` 的那一页，没有就用 `LIST_LINEAR` + 首页 `card` 兜底 |
| `query` / `submitted` | 输入框里的字 vs 已提交的关键词。空态文案读 `submitted`，所以"改成另一个词但没按搜索"时列表不会假装是新结果 |
| `state: FeedUiState` / `requestId` | 结果状态；`requestId` 每次 `submit`/`retry` 自增，`LaunchedEffect` 靠它触发——**同一个关键词再按一次也会重搜** |
| `updateQuery()` / `submit()` / `retry()` | 改名自 `setQuery`：`var query` 的属性 setter 在 JVM 上就叫 `setQuery`，同名函数会 `Platform declaration clash` |
| `load()` / `loadMore()` | 首屏与翻页；追加时按 id 去重，整页都是重复就判到底 |

**关键词怎么进请求**（`SourcePipeline.search()`）：模板只做字符串替换、不做编码，用户输入 `你好 & 世界 #1`
会把 URL 拼坏（`&` 直接切断参数）。所以注入两个变量：

- `{{keyword}}` = `value.encodeURLParameter()`（Ktor 3.x；没有 `encodeSlash` 参数）
- `{{keywordRaw}}` = 原值，给 POST body 这类不需要编码的位置用

单测 `SearchPipelineTest`（2 例）用 `MockEngine` 断言"URL 的 `q` 参数解码后等于原词、`page=1`、命中 search 资源"与
"body 里保留原值"。

**页面 UI**：一行 `OutlinedTextField(singleLine, ImeAction.Search, trailingIcon=「清空」)` + 「搜索」按钮；
`searchKey == null` → "这个源没有配置搜索"；`submitted` 为空 → "搜点什么"；有词 → `UmpPage(showTitle = false,
emptyTitle = "没有搜到「$submitted」")`——复用首页那套列表/空态/翻页，只是空态文案换了（`UmpPage` 为此加了
`emptyTitle`/`emptyHint` 两个参数）。

**不做的**：多源搜索（`flags.multiSourceSearch` 已从 Schema 删除，见 `docs/03 §12.1`）。
搜索历史已接线（2026-11-18，`docs/04 §8.8`）：`LayoutSpec.historySize` 字段仍未被配置读取，条数固定 12 条/源。
输入防抖支持配置的 `debounceMs`（不写 = 0 = 不自动搜，只认回车/按钮）。

### 8.0.1 画面怎么挂上去：`renderToken` + `surface` 槽位

播放器抽象之后还剩一个问题：**ExoPlayer 的画面要落在哪块 UI 上**。
三条约束同时成立：`core:player` 的 common 侧不能出现 Media3 符号；`render` 不能依赖播放器实现；
`feature:main` 是 commonMain，拿不到 Android 的 `AndroidView`。

做法是不动模块依赖图，只在调用链上开一个槽位：

```kotlin
// 1) core:player：只交出不透明句柄
interface PlayerFacade { val renderToken: Any? get() = null }   // Android: ExoPlayer；桌面: null

// 2) render.UmpPlayer：纯 Compose 槽位，仍不含播放器符号
surface: @Composable (Modifier) -> Unit = {}

// 3) feature.AppRoot：把壳层实现透传下去
playerSurface: @Composable (Any?, Modifier) -> Unit = { _, _ -> }

// 4) app:android：唯一出现 Media3 的地方
AppRoot(sources, playerSurface = { token, m -> Media3Surface(token, m) })
```

画面叠放顺序：`封面(poster) → surface(视频) → 播放/暂停按钮`。封面当"未起播时的底图"，起播后视频盖住它，
按钮永远在最上层——一块 UI 同时表达"没播 / 在播 / 出错"三种状态。

**明文流量必须按域白名单**：示例视频源的 mp4 直链是 `http://`（`cdn.example.com` 这类 CDN 不走 https），
而 Android 默认 `usesCleartextTraffic=false`，ExoPlayer 连请求都不发就报 `[P2007]`
（Media3 的 `IO_CLEARTEXT_NOT_PERMITTED`）。修法不是全局开明文，而是
`app/android/src/main/res/xml/network_security_config.xml` 里 `base-config` 保持 `false`，
只对配置里声明的图片/视频域名开 `cleartextTrafficPermitted="true"`。
新增站点若也用 http 直链，在那里补域名。

### 8.0.2 播放器控件版式（M4 第二批 → 第四批定稿；M6.5 改成主流排法）

**三条用户反馈定下的版式原则**：① 常驻按钮不许压在画面正中；② 控件要在画面里、但没事时自己消失；
③ 控件按"别的 App 的样子"排，别让用户为这个 App 重新学一遍（M6.5）。

```text
┌────────────────────────────────────────┐
│ ← 第1集                        （顶栏）│  ← 往下滚离顶部时整条收起（M6.5）
├────────────────────────────────────────┤
│  [      画面（高度 ≤ 可视区 62%）    ]  │  ← 画面上不留常驻按钮
│  ┌────────────────────────────────┐   │
│  │ ( ▶) ‹10s  10s›  1.0x ▾  全屏  │   │  ← 控制条只有这一行按钮；进度条已拿掉
│  └────────────────────────────────┘   │
│  ▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬  │  ← 常驻：画面底沿 3dp 色条，长短=进度，点哪跳哪
├────────────────────────────────────────┤
│  标题                                  │
│  01:33 / 02:15 · 播放中   连续播放 ( ○) │  ← 时间读数挪到状态行；右侧连续播放开关
│  [复制播放地址]                        │
└────────────────────────────────────────┘
```

取舍（前五条是 M4 定下的，后面是 M6.5 补的）：

| 做法 | 为什么 |
|---|---|
| **画面上一个常驻按钮都不留**（中央那颗半透明播放键也删了） | 它和叠层里的「播放」本来就重复；又因为叠层贴在画面底部、画面只有 1/3 屏高，中央正好落在进度条那条线上，暂停时看着就是"进度条背后压着一个按钮"。暂停时控制层常亮，入口一直在，不需要第二个 |
| **控件从"画面下方"搬进"画面底部叠层"** | 竖屏里画面下方的控制条和画面隔着半个屏幕，手要跨屏去点。叠在底部压的是片尾字幕安全区，不是画面正中 |
| **播放中静置 3s 自动淡出，点画面唤回** | 一条 16:9 画面在手机上只占 1/3 屏高，控件常驻既浪费又挡内容；"先看、要看操作时再点出来"是视频 App 的通行做法。暂停/出错时**不隐藏**，否则找不到"继续" |
| **画面内那颗「全屏」按钮已删除** | 用户先后两次反馈"控件压画面"；挪到右上角照样挡内容。进全屏的唯一入口就是控制条上的「全屏」 |
| **倍速从 4 个 chip 改成下拉** | 720×1280 上 4 个 chip 必换行；下拉展开时浮在上方、不占布局高度 |
| **M6.5 控制行改成"播放键最左 + 快进快退紧跟 + 倍速/线路/全屏靠右"** | 旧版把「暂停」放在正中间、快退快进丢到两头，看着像自制控件。长视频与会员视频类源通常都是播放键在最左。用户上手过别的播放器，不该为这个 App 再学一遍 |
| **M6.5 控制条里那颗进度滑块直接删掉** | 用户："把控制条里的进度条去掉"。滑块是 M3 时代"必须有拖动"的产物：48dp 高的一条横贯画面、两端还挂时间，把控制行挤到第二行。进度改由底沿那条色条表达后，滑块就是重复 |
| **M6.5 进度只靠"颜色条长度"，不加分隔/刻度/竖线** | 用户："不用添加 \|，直接控制颜色条长度就行"。所以只有一个主色段 + 一条几乎透明的轨道，没有 thumb、没有节点、没有 `|` 这类分隔符。播到哪儿看色条到哪儿，够用了 |
| **M6.5 色条常驻、并且可点（点哪跳哪）** | 滑块删掉之后，只剩 ±10s 就没法"跳到某个位置"。色条的触摸区做成 14dp 高（视觉仍是 3dp，3dp 的线手指点不中），点哪算哪的比例；实测点 30% 处 → `00:40 / 02:15`，比例准确。它比画面其它区域优先拿手势，所以点色条是 seek、点画面才是切控制层 |
| **M6.5 时间读数从滑块两端挪到状态行** | 滑块带着"左已播、右总长"一起没了，但精确到秒的读数不能丢。状态行原来那句 `时长 02:15` 改成 `01:33 / 02:15`，一眼还是"到哪儿了、还剩多久"，且不占画面 |
| **M6.5 给画面加高度上限（可视区 62%）** | 竖屏短剧按 9:16 铺满宽度时高 1166px，一屏只有 1280px：叠在画面底部的控制条被顶到屏幕外，点画面根本看不见控件（实测如此），色条也一起出去了。到上限就按比例缩窄、两侧留黑，控件永远在屏幕里 |
| **M6.5 播放页滚离顶部时收起顶栏** | 用户反馈"下滑的时候最上面的组件没隐藏"。一屏放不下"画面 + 标题 + 选集"，往下滑看选集时顶栏还占 112px。改成 `scrollState.value > 12` 时收起、滚回顶部放出来，`AppRoot` 用 `expandVertically/shrinkVertically` 过渡；只在播放页生效（别的页顶栏是返回和标题，滚走反而找不到路） |

**连续播放开关（M6.4，2026-11-16）**：那个"播完自动接下一集"的行为以前是读配置
`playback.player.autoNext`（默认 `true`），等于作者替用户决定。现在改成**用户级全局开关**：

| 项 | 落点 / 口径 |
|---|---|
| UI | `UmpPlayer` 状态行右侧：`时长 03:25 · 播放中` 的右边跟一个 `Switch`（`onAutoNextChange` 为 null 时不画） |
| 状态 | `AppRoot` 里 `var autoNext`，初值 `settings.getString(SettingsKeys.PLAYER_AUTO_NEXT) == "1"`，默认 **false** |
| 落盘 | 拨动时 `settings.putString(PLAYER_AUTO_NEXT, "1"/"0")` —— 与"上次选的源"同一套 `AppSettings` |

| 为什么不放控制条 | 控制条在播放中 3s 自动淡出；"要不要连播"是设置类操作，不该跟着视频一起消失 |
| 为什么放状态行而不是设置页 | 用户是在播放页想到这件事的（刚看完一集、想不想接着看），放在这里零跳转 |

实现上有个坑：`LaunchedEffect(state.status, url)` **只在 key 变化时重启**，直接把 `autoNext`
捕获进闭包会拿到进入页面时的旧值——播放中途拨开关不会立即生效。两处路由都改成
`val latestAutoNext by rememberUpdatedState(autoNext)`，`ENDED` 时读最新值。

一个编译上的坑（值得记）：色条最初放在 `Column` 里的画面**下方**，直接写
`AnimatedVisibility` 会被解析成 `ColumnScope.AnimatedVisibility` 而报
"cannot be called in this context with an implicit receiver"；抽成独立 composable 才会用顶层那个版本。
后来因为它落在屏幕外（竖屏画面占满一屏），改成贴着画面底沿并常驻，`AnimatedVisibility` 也不再需要。

**"在不在播"不能用 `player.isPlaying` 判**（这条是踩出来的）。

Media3 的 `isPlaying` 会被音频焦点抑制等情形打成 `false`，而时间码照旧在走：
模拟器实测位置从 `00:36` 涨到 `00:49`，状态却停在「就绪」，连带"3 秒自动隐藏"永远不触发。
`core/player` 的 Android 实现因此改成按语义判定，并让 ticker 每 250ms 一起刷状态
（事件漏触发时界面也不会卡在旧态）：

```kotlin
private fun computeStatus() = when {
    player.playerError != null -> ERROR
    player.playbackState == STATE_ENDED -> ENDED
    player.playbackState == STATE_BUFFERING -> PREPARING
    player.playbackState == STATE_READY && player.playWhenReady -> PLAYING
    player.playbackState == STATE_READY && positionOf() > 0L -> PAUSED
    player.playbackState == STATE_READY -> READY
    else -> IDLE
}
```

**全屏状态必须由路由层持有，否则返回键顺序是错的**（M4 第三批）。

`fullscreen` 原先只是 `UmpPlayer` 内部的 `remember`，路由层看不见。于是按系统返回键时，
`AppRoot` 注册的 `BackHandler`（语义是"从播放页返回详情"）先被触发 —— 用户想退全屏，却直接掉回详情页。

修法是把状态提升上去，而不是在 `AppRoot` 里加判断：

| 层 | 职责 |
|---|---|
| `UmpPlayer` | 新增 `fullscreenState: MutableState<Boolean>? = null`：不传就自己 `remember`（组件仍可独立使用）；传了只读写外部那一份 |
| `PlayerRoute` | `remember(item.id) { mutableStateOf(false) }` 持有，并 `backDispatcher(fullscreenState.value) { fullscreenState.value = false }` 把自己注册到**比 AppRoot 更晚**的位置 |
| `AppRoot` | 把同一个 `backDispatcher` 再往下传一层（`playing != null` 分支） |

依赖的是 Compose `BackHandler` 的**后进先出**：`PlayerRoute` 的注册点在组合树里更深、执行更晚，所以先拿到返回键。
全屏为 `false` 时它 `enabled = false`，返回键自然落回 `AppRoot`，走"退出播放页"这条老路 —— 一层不写两套逻辑。

> **全屏要真的全屏**：状态再由 `AppRoot` 持有一份（`fullscreenState`），全屏时把 `AppTopBar` 整块不组合，
> 画面才铺满整屏。`LaunchedEffect(playing)` 在换条目/退出播放页时把它归零，
> 否则从上一条的全屏里"继承"进新页面。实测：全屏后顶栏消失，按一次返回回到非全屏播放页（顶栏回来），
> 再按一次才回详情。

**系统栏也要收起来，否则"全屏"只是画面变大一点**（M4.4 续）。

只隐藏 `AppTopBar` 时，Android 的状态栏与导航栏还在，画面并没有占满屏。隐藏系统栏是
Window 级 API，而 `render` / `feature` 都是 commonMain，拿不到 Activity 的 `window`，
所以链路必须跨一层：

```
UmpPlayer 控制条「全屏」→ fullscreenState=true
  → AppRoot.LaunchedEffect(fullscreenState.value) → onFullscreenChange(true)
    → MainActivity.applyImmersive(true)
```

| 位置 | 职责 |
|---|---|
| `AppRoot.onFullscreenChange` | 新增参数 `(Boolean) -> Unit = {}`，桌面端留空（那边只是窗口内铺满） |
| `MainActivity.applyImmersive` | `setDecorFitsSystemWindows(false)` + `systemBarsBehavior = BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE` + `hide(systemBars())` |

两件事必须一起做：

- 只 `hide()` 不 `setDecorFitsSystemWindows(false)`：系统栏消失了，但内容不会延伸到它原来的位置。
- 退出时**必须**把 `setDecorFitsSystemWindows` 恢复成 `true`，否则首页顶栏会被状态栏盖住。

`BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE` 让用户在全屏里从边缘上滑能临时唤出系统栏、
几秒后自动消失 —— 视频类 App 的通行做法，避免全屏状态下完全失去系统手势提示。

实测（720×1280 模拟器）：点「全屏」后状态栏、导航栏全部消失，画面整屏铺满（16:9 视频在 20:9 屏上的上下黑边属正常留黑）；
`uiautomator dump` 中该按钮已变为「退出全屏」，位置从画面内 y≈489 移到屏幕底部 y≈1200。

**进播放页就直接放**。只 `prepare()` 不 `play()` 会停在 0 帧（或停在续播点上不动），
用户还得再点一次「播放」——实测就是这么卡住的（状态显示「已暂停」而画面不动）。
`PlayerRoute` 因此在 `prepare` 之后立刻 `play()`：用户本来就是点了「播放」才进来的。

**播放地址的"裸 IP 归一化"放在配置层，不在播放器里**。

同一详情接口的两条数据通路，返回的 CDN 主机不一样：

| 通路 | `ul.ui[0].url` |
|---|---|
| 按条目 id 取详情 | `http://cdn.example.com/...`（域名，白名单覆盖） |
| 按专辑 id 取详情 | `http://203.0.113.10/cdn.example.com/...`（**裸 IP 前缀**） |

裸 IP 无法加进 `network-security-config`（Android 不支持 IP 通配），于是 `[P2007] IO_CLEARTEXT_NOT_PERMITTED`。解法是用配置里已有的 `rewrite`（变换链对 `template` 结果同样生效）：

```jsonc
"playUrl": {
  "kind": "template",
  "parts": ["{{$.ul.ui[0].url}}", "{{$.fn}}", "?vkey=", "{{$.播放凭证字段}}"],
  "rewrite": [
    { "pattern": "http://[0-9]{1,3}\\.(?:[0-9]{1,3}\\.){2}[0-9]{1,3}/", "replacement": "http://" }
  ]
}
```

结果 `http://203.0.113.10/cdn.example.com/...` → `http://cdn.example.com/...`（域名在白名单内）。

**为什么不在播放器侧做 host 替换**：那是站点知识，进了 `core:player` 就把"通用播放器"变成"某个源专用的播放器"；
而 `rewrite` 是配置语言里本来就有的能力（见 §4.3 变换链），挪过去零成本。

### 8.1 平台抽象层总览（6 个 expect）

播放器不是唯一需要按端实现的东西。整个"平台抽象层"一共 6 个 `expect`（完整矩阵见 `docs/06`），`core:player` 只负责其中一个：

| expect | 所在模块 | 为什么必须分平台 |
|---|---|---|
| `PlayerFacade` | `core:player` | 每端原生播放器完全不同 |
| `HtmlParser` | `core:query` | iOS / Web 没有 Jsoup |
| `KeyValueStore` | `core:storage` | DataStore / prefs / NSUserDefaults / localStorage |
| `DatabaseDriver` | `core:storage` | SQLDelight 各端驱动不同 |
| `FileGateway` | `feature:main` | 文件选择与分享是系统级能力（SAF / FileDialog / UIDocumentPicker） |
| `PlatformInfo` | `core:common` | 断点、输入类型、是否 TV |

**分层原则**：`core:player` 的 `commonMain` 只声明契约与策略（`PlayResolver`），**不出现任何 Media3 / AVPlayer 符号**。这样新增一端时不需要动 common 代码。

**图片不进 `core:player`**：图片没有"播放"语义，它走 `core:ui` 的 `ImageViewer`
（Compose 手势 + Coil 加载），只有 `kind=video|audio` 才创建 `PlayerFacade`。
这样纯图片源不需要任何播放器依赖，桌面/Web 端也不必为看图准备解码器。

### 8.2 `PlayerFacade` 契约（含能力自描述）

```kotlin
expect class PlayerFacade {
    val state: StateFlow<PlayerState>
    /** 多端关键：播放前就能知道"这端能不能放" */
    val capabilities: PlayerCapabilities
    fun prepare(url: String, headers: Map<String, String>, kind: MediaKind, startMs: Long = 0)
    fun play(); fun pause(); fun seekTo(ms: Long); fun setSpeed(x: Float); fun release()
}

data class PlayerState(
    val status: Status,          // IDLE | PREPARING | READY | PLAYING | PAUSED | ERROR | ENDED
    val positionMs: Long,
    val durationMs: Long,
    val error: PlayError?,
)

data class PlayerCapabilities(
    val formats: Set<String>,       // "hls" | "mp4" | "mkv" | "flv"
    val supportsHeaders: Boolean,   // 能否注入 Referer / Cookie
    val supportsSpeed: Boolean,
    val supportsHls: Boolean,
)
```

**为什么要 `capabilities`**：UI 必须在播放**之前**判定可行性。
先放下去再黑屏，用户只会认为是 App 坏了；提前判定 + 明确提示，才是可用的多端体验。

### 8.3 各端 actual 实现要点

| 端 | 实现 | 关键约束 |
|---|---|---|
| Android | Media3 `ExoPlayer` + `DefaultHttpDataSource` 注入 headers | HLS 原生；硬解失败降级软解；横竖屏由 Activity 的 `requestedOrientation` 控制 |
| Desktop | **vlcj 4.8.2 + 本机 libvlc**（M7.5 已落地）；JavaFX Media 作为备选未采用 | 运行期依赖本机装 VLC；视频面是 heavyweight AWT `Canvas`，会盖住 Compose 叠层 |
| iOS | `AVPlayer` + `AVURLAsset` 的 `HTTPHeaderFields` | HLS 原生，mkv 不支持 |
| Web | `<video>` + 手动 fetch m3u8 | 受 CORS 限制；HLS 需 hls.js 或浏览器原生支持 |

#### 8.3.1 桌面端：vlcj 驱动本机 libvlc（M7.5）

**为什么是 vlcj**：桌面端只有 Windows 一个目标，VLC 基本都是装好的；Media3 没有桌面版；JavaFX Media 对 m3u8/mkv 支持差。
vlcj 只是 libvlc 的 JNA 封装，解封装/解码/字幕/倍速全交给 VLC，行为等价于"用 VLC 打开这个 URL"。

```kotlin
MediaPlayerFactory("--no-video-title-show", "--quiet")
  .mediaPlayers().newEmbeddedMediaPlayer()
  .also { it.videoSurface().set(factory.videoSurfaces().newVideoSurface(canvas)) }
```

- **`renderToken` 交出 AWT `Canvas`**，壳层用 Compose `SwingPanel` 挂载；`token == null`（占位实现）时铺黑底 `Box`。
- **事件映射**：`opening`→PREPARING、`playing`→PLAYING、`paused`/`stopped`→PAUSED、
  `timeChanged`→positionMs、`lengthChanged`→durationMs、`finished`→ENDED、`error`→`P2007`。
- **续播点只能在 `playing` 事件里 seek**（用 `pendingStartMs` 暂存）。VLC 在 playing 之前没有有效位置，
  起播前 seek 会被静默丢掉——这是最容易写成"续播不生效"的一处。
- **能力如实声明**：`formats = mp4/mkv/flv/ts/hls`、`supportsSpeed = true`、`supportsHls = true`、
  **`supportsHeaders = false`**（vlcj 加 Referer 要拼 `:http-referrer=` 的 media option，当前源用不到）。
- **两个必踩的坑**：
  1. vlcj 在 Windows 靠**注册表**找 VLC 目录，链路依赖 `jna-platform`，而它**不随 vlcj 传递**。
     缺了会抛 `NoClassDefFoundError: WinReg` → `discover()` 返回 false → UI 显示"未找到 VLC"，
     看起来像"接入没生效"，其实是缺依赖。
  2. vlcj 的画面是 **heavyweight** 的，绘制在 Compose 画布**之上**：叠在画面里的控制条会被视频整块盖住。
     解法是 `UmpPlayer` 的 `controlsBelowSurface = true`——控制条移到画面下方常驻；
     手机端保持默认 `false`（叠层 + 静置 3 秒自动隐藏），两端因此各用各的版式而共用同一套控件。
  3. **不要在 vlcj 的事件回调里调用 libvlc 的 API**。回调跑在 libvlc 的事件线程上，在里面读
     `video().videoDimension()` / `status().length()`（为了拿视频尺寸）会**阻塞事件线程**：
     状态机再也走不到 `PLAYING`，界面永远停在「准备中…」、画面全黑，而日志里一句错都没有。
     正确做法是事件回调只做纯状态标记，读数交给一个 250ms 的独立协程 ticker
     （`startTicker()`，与 Android 端同一节奏），**续播 seek 也放在 ticker 里执行**。

**画面比例跟随视频尺寸**：`PlayerState` 带 `videoWidth/videoHeight`（起播后由解码器解出），
`UmpPlayer` 用 `state.videoAspect ?: 16:9` 决定画面容器比例，并且**一旦有进度就不再画封面图**
（封面只在"还没起播"时当底图）。原因是：容器写死 16:9 时，竖屏短剧 / 4:3 老片会留边，
而封面图正画在视频下面，留边处就把海报透了出来——用户看到的正是"视频背景里有张图"。

**实测（`00:29/03:25` → `01:32/03:25`，画面内容同步切换）**：桌面端首页→详情→播放全链路走通，
控制条在画面下方可见、未被 VLC 的视频面遮挡。另有一条自动化经验：截图分辨率（2048 宽）
与屏幕物理像素（2560×1080）不同坐标系，按截图坐标点击会整体偏；
要用 `GetWindowRect` 取窗口物理矩形，按**窗口内相对比例**换算。

Android 实现（headers 注入是最容易踩坑的一处）：

```kotlin
actual class PlayerFacade(context: Context) {
    private val player = ExoPlayer.Builder(context)
        .setMediaSourceFactory(
            DefaultMediaSourceFactory(
                DefaultDataSource.Factory(context, httpFactory(headers))
            )
        ).build()
}
```

- **headers 注入**：`ResolvingDataSource` + `DefaultHttpDataSource.Factory().setDefaultRequestProperties(headers)`。
  多数 CDN 校验 `Referer`，没有它直接 403。
- **m3u8**：`DefaultMediaSourceFactory` 自带 HLS 支持；`MediaItem` 的 `MimeTypes.APPLICATION_M3U8` 可选显式标注。
- **竖屏/横屏**：Activity 级 `requestedOrientation`，播放器本身不感知。
- **息屏续播**：`setWakeMode` + 前台服务（v2）。

### 8.4 能力探测与降级（多端的核心机制）

```
选中某集 → 得到 PlayRequest
   ↓
PlayResolver.resolve()            → 直链，或解析接口返回的真实地址
   ↓
capabilities.supports(format) ?
   ├─ 是 → player.prepare()
   └─ 否 → 降级链：
           ① strategy=direct 时，先尝试走 resolver 取 mp4 直链；
           ② 仍不行 → 提示"当前平台不支持 {format}，可在 Android/桌面端播放"；
           ③ 能力不足的原因写在页面上的提示里（调试器已删除，不再单独采集）。
```

**关键**：能力不足必须**可解释**。
用户看到"不支持"时要能分辨是"平台限制"还是"配置写错"——两者的修复动作完全不同（换端播放 vs 改配置）。
同样机制适用于抽取器：`kind=css` 在无 HTML 解析能力的端降级为"文本 + 正则"（见 `docs/06` §3）。

### 8.5 `PlayResolver`：两段式

```kotlin
class PlayResolver(
    private val http: HttpEngine,
    private val schema: CompiledPlayback,
) {
    suspend fun resolve(rawUrl: String, headers: Map<String, String>): Outcome<ResolvedPlay> =
        when (schema.strategy) {
            Strategy.DIRECT -> Outcome.Ok(ResolvedPlay(rawUrl, headers))
            Strategy.RESOLVER -> {
                val req = buildRequest(schema.resolver.request, mapOf("url" to rawUrl))
                val body = http.fetchText(req)
                val real = schema.resolver.extract.eval(body)
                if (real != null) Outcome.Ok(ResolvedPlay(real, headers))
                else Outcome.Fail(StageError(E102, "解析接口未返回地址"))
            }
        }
}
```

`strategy` 放在配置层，用户视角始终是"点选集就能播"，差异被吸收。

**落地状态（2026-11-14）**：`PlayResolver` 目前只有设计，`feature:main` 的 `PlayerRoute` 是把
`PlayTarget.url` 直接喂给播放器（`docs/02` F6.2 因此仍是待办）。现有示例源都不需要它：
示例视频源 `详情接口` 的 `播放凭证字段` 拼出来就是直链，示例短剧源的 `episodes.item` 已经把 m3u8 解析进 `Track.url`。
真要用它（第三方解析接口 / 需要签名的站点）之前，必须先补三件事，否则"解析"只能覆盖最简单的 GET：

| 缺口 | 为什么必须有 |
|---|---|
| `resolver.request` 支持 `method` / `body` / `bodyType` | 示例短剧源这类播放接口是 `POST {}`，`GET` 直接 404；只支持 GET 的 resolver 解析不了 |
| `TemplateEngine` 支持 `{{url\|raw}}`（当前**未实现**） | 把整条地址当 query 参数丢给第三方解析服务时，编码过的 URL 有些服务解析不出来。现状：`render()` 的正则只认 `[A-Za-z0-9_.]+`，`{{url\|raw}}` 既不被编码也**替换不掉**，会原样留在 URL 里——写进配置等于配错，所以这条和上一条必须一起补 |
| 响应里取鉴权头（`headersFrom`） | 有的站点把 `x-cdn-auth` 放在播放响应里，静态 `playback.headers` 表达不了（`docs/03 §10.1`） |

> 模板编码的现状（M6.3 核对）：`TemplateEngine.render()` **只做字符串替换，不做 URL 编码**。
> 全仓库唯一"先编码再注入"的变量是搜索关键词 `{{keyword}}`（`SourcePipeline.search()` 里过 `encodeURLParameter()`）。
> 想给别的变量加编码，应当像 keyword 一样在**注入方**（管线/页面）编码，而不是改 `TemplateEngine`——
> 它同时服务于 body 与 prefix/suffix，统一编码会把 JSON body 也改坏。

### 8.6 失败兜底链（跨端通用）

```
播放失败
  → 能力不支持？ → 走 8.4 的降级链
  → 同一线路重试 1 次（换 CDN 节点 / 清 header）
  → 换同组下一线路（同集）

```

### 8.7 图片查看器（落地在 `render` 的 `ImageViewerView`，M4.6 → M6.6 重做）

图片不是"播放"，是"浏览"，所以它不走 `PlayerFacade`，也不在 `core:ui`（那里只有主题与通用组件）：

```kotlin
// render/src/commonMain/.../render/ImageViewerView.kt
@Composable
fun ImageViewer(
    title: String,
    tracks: List<Track>,      // 图集懒取时这里是 60 条 url 为空的占位（pending 非空）
    startIndex: Int,          // 有进度就落到进度那张，否则用详情页点的那一张
    onBack: () -> Unit,
    onIndexChange: (Int) -> Unit,                             // 回写 viewing.trackIndex + 存进度
    loadPending: (suspend (Int, String) -> Track?)? = null,   // 懒取一张：拿到直链才返回
)
```

**手势（M6.6 定稿，四种都要成立）**

| 手势 | 行为 | 实现要点 |
|---|---|---|
| 上下滑 | 上滑下一张、下滑上一张（竖屏漫画是"往下读"） | `VerticalPager` 原生处理，页面层不拦 |
| 左右滑 | **右滑前进、左滑后退**（与上下滑同向语义），**拖动跟手**：当前页横移、目标页从边上滑入 | 外层 `detectHorizontalDragGestures` 只接管横向占优的拖动，把位移换算成 `hProgress`（-1..1）；松手过 28% 用 180ms `tween` 补齐到 ±1 → `scrollToPage` 落到目标页并把位移归零（新页正好停在邻居层刚滑到的位置，所以是连续切换而不是跳一下），未过 28% 回弹到 0 |
| 双指缩放 | 1x–4x，放大后可平移、平移限制在"图不出画面" | 手写 `awaitEachGesture`（见下） |
| 点页码 | 弹"跳到第几张"，输入后直达 | 工具条页码即按钮 |

**为什么不能直接用 `detectTransformGestures`**：它在**单指**下也会 `consume()` 全部 pointer 事件，
`Pager` 便永远收不到拖动 —— 实测表现是"上下滑不动，只能看到第一张"。
正解是 `awaitEachGesture` + 自己判条件：**只有 `event.changes.size >= 2`（多指）或已放大（`scale > 1.01f`）才消费**，
单指未放大时把事件原样让给 Pager（横向只累计位移、不消费）；放大状态下同时把 `userScrollEnabled` 置 false，
变成"先平移、缩回 1x 才能翻页"。

**加载策略：预加载窗口（可调，默认"之后 3 张"）**

- `episodes.lazyItems=true` 时 `Track.url` 为空、只有 `pending` 占位 id；进详情**不请求任何内页**（当时实测日志 `[detail] … tracks=60 lazy=60`，后来同一图集是 455 条）。
- 每页在 `LaunchedEffect(page, pendingId, near, retryTick)` 里按需调 `loadPending`，结果写进 `mutableStateMapOf<Int,String> urls`。
- ⚠️ **只靠 `beyondViewportPageCount` 挡不住**：Pager 自己判断要不要预组合，实测一次进图集日志里连续解析了 13 张。
  所以真正把关的是**硬限窗**：只有 `page ∈ current..(current + N)` 的页才取址/解码，其余只画空 `Box`；
  `near` 写进 effect 的 key，翻页即重算。窗口大小 `N` = 设置里的「预加载张数」（默认 3，0..8），细节见本节末"预加载张数"。
- 三态提示（用户要的"加载动画/进度"）：`url == null` → "正在获取图片地址" + 转圈；Coil `Loading` → "加载中" + 转圈；
  **失败两种都能点按重试**：Coil `Error` → "这张图加载失败 · 点按重试"（点一下只重载这一张：`reloadTick++` 改
  `ImageRequest.memoryCacheKey` 强制重新请求，已加载成功的页 model 没变、命中缓存不会重下）；
  取址失败 → "图片地址获取失败 · 点按重试"（**点一下重新解析一次**，线上站点跳页时出现过 `ok=false`，翻走再翻回不会自动重试）。

**底部工具条：一行（高度问题已修）**

早期版本是"页标签 / 按钮 / 提示"三行，实占 110dp 以上，用户原话是"上下滑动切换 双指缩放 占用高度太高"。
现在只留一行：`⇤  ▲  页码（可点跳转）  ▼  ⇥` + 行尾灰字"双指缩放"（放大时换成"复位"）。
按钮统一 44dp 触摸宽度（工具条压成一行后按钮变窄，靠 `minTouch()` 补回来）。
顶栏同样只一行：返回 / 标题 / `N / M`，不隐藏。

**页码跳转**（`AlertDialog`）：标题"跳到第几张"，输入框只收数字（`filter { it.isDigit() }`，最多 6 位），
label 显示 `1 - N`，确定走 `goTo(input - 1)`（内部 `coerceIn` + `animateScrollToPage`）。

**进度**（与视频/音频的 `positionMs` 是两套语义）：图片只记"看到第几张"，键 `image.progress.<源id>.<条目id>`，值 = 页索引（0 起）。
进查看器时 `startIndex = if (viewing.trackIndex > 0) trackIndex else settings.getString(progressKey)?.toIntOrNull() ?: 0`；
`onIndexChange` 里同时回写 `viewing.trackIndex` 与 prefs。实测（当时 60 项那版）：跳/翻到第 20 张后返回再进"开始阅读"，直接落在 `20 / 60`，
prefs 里对应键为 `19`。

**接线路由**（这层不写在 render 里，避免渲染层依赖 feature）：

| 环节 | 落点 |
|---|---|
| 详情页点哪张 | 图集页数 > `IMAGE_GRID_MAX`(12) 时**不铺网格**，只渲染"开始阅读"横幅（`DetailView.ImageEntryBanner`）；页数少仍铺 `ImageGrid` |
| 判定进查看器而不是播放 | `DetailRoute.onSelectTrack`：`track.url.isNotBlank() || item.kind == MediaKind.IMAGE` → 查看器，否则播放 |
| 懒取接线 | `AppRoot` 从 `session.schema.pages` 取 DETAIL 页的 `layout.resource` 当 detailKey，调 `pipeline.resolvePendingTrack(...)` |
| 路由状态 | `AppRoot.viewing: PlayTarget?`；`onBack` **最优先**清它（先于播放页、先于详情页） |
| 换源 | `viewing` 与 `playing` 一起清空 |

示例源：`samples/` 里的图集示例配置（图集走 `episodes.lazyItems=true`，见 docs/03 §5.5.5；条目数按列表页总数抓全，见 §5.5.6）；
`samples/` 里的壁纸示例配置（壁纸示例源每日壁纸，`tracks` 走 `array` 形态、无 pending，见 docs/03 §7.3.2）。

**预加载张数（2026-11-18，口径由用户确认）**：`ImageViewer(preload = N)`，`N` = 当前张**之后**预取几张，
来自设置 `SettingsKeys.IMAGE_PRELOAD`（0..`IMAGE_PRELOAD_MAX`=8，默认 3）。例：设 3 → 看第 1 张时加载 1、预加载 2/3/4；
看第 15 张时加载 15、预加载 16/17/18。两处都跟着它走：`beyondViewportPageCount = N` 与硬限窗
`page in current..(current + N)`——只改前者挡不住 Pager 自己多组合，所以真正决定"取几张"的永远是硬限窗。
**只往后、不往前留**：回看靠已经取到的直链（`urls`）+ 图片缓存，翻回去不重新发取址请求；往前预留等于每次多打一倍的请求，
而往回复看是少数动作。`N=0` 是"滑到下一张才开始取址"；`N=8` 是同时最多 9 张。上限取 8 是因为再大等于进图集就把一大片内页请求打出去。

**条目数必须等于网页**（2026-11-18 补）：这本 455 张的图集暴露的问题不在渲染，而在 `fetchIdPages` 的页数上限——
原来 `maxPage=3` + `maxItems=60` 把"图集有多大"交给配置猜，网页 455、App 只有 60（标题读的是详情页的 `Length`，所以显示 455 页，格子却是 60 项）。
现在第 1 页 id 表同时读出总数（`paging.totalPattern`），`pages = ceil(total / perPage)` 再分块并发抓其余页，
`maxPage` 只作安全阀；抓不到总数才退回逐页 `emptyStop` 兜底。
`maxItems` 也不再是分页上限：它只是"防配错"的保险丝，抓到总数时取 `max(maxItems, total)` 作为截断值，
否则老配置里残留的 `maxItems:60` 会把已经抓全的 455 条重新砍回 60（2026-11-18 补，回归见 `EpisodeCountTest.maxItemsIsSafetyValveNotPaginationLimit`）。
实测口径：455 张 = 23 个 `?p=0..22` 请求，`concurrency=6` 分 4 批；`[ids] total=455 perPage=20 pages=23`，`[detail] … tracks=455 lazy=455`。
查看器侧无需配合——它按 `tracks.size` 决定 `1 / N`，N 一变就跟着变。

### 8.7.1 密文封面：图片管线上多一道解码（示例短剧源实测，2026-11）

`AsyncImage(model = poster)` 在这类源上会**静默失败**：CDN 返回的是 AES 密文（`binary/octet-stream`），
Coil 拿到字节 → 找不到图片头 → 交回错误 → 卡片上留一个灰块，日志里也未必有声。
配置口径与实测证据见 `docs/03 §3.2`，这里只说实现。

**落点选"图片管线的统一入口"，不选页面**：图片通路只有一条，改一次就覆盖卡片、详情海报、图集缩略图、
查看器大图。页面级各改一遍必然漏掉一两处（漏掉的那处只会变成灰块，不会报错）。
落地做法是把 render 里 9 处 `AsyncImage(...)` 全部换成 `UmpAsyncImage(...)`（`render/…/ImageDecrypt.kt`）。

**为什么不是 Coil 的 `Fetcher` / `Interceptor`（2026-11-16 两次实测判死，别重走）**：

| 路线 | 实测结果 |
|---|---|
| `Interceptor` | Coil3 的 `ImageResult` 只有 `image` / `request`，**拿不到 `ImageSource`**，改不了字节 |
| 全局 `ImageLoader.Builder.components { add(Factory()) }` | 密文 URL 依然走原生 `NetworkFetcher`（logcat 里还在打 `DiskLruCache`），自定义 `create` 一次未被调用 |
| 请求级 `ImageRequest.fetcherFactory(Factory, String::class)` | 同上：`create` 依然没被调用（`compose model=… spec=…` 打印了 9 次，`create hit` 零次） |

结论：Coil3 3.3.0 里自定义 fetcher 抢不过内置的 `NetworkFetcher`。**字节在进 Coil 之前就解好**，
绕开整个优先级问题：

```kotlin
// render/src/commonMain/kotlin/com/vi/ump/render/ImageDecrypt.kt（实际实现，非草图）
val bytes by produceState<ByteArray?>(null, url, revision) {
    value = DecryptedImageStore.load(url, spec, UmpImageDecrypt.headers)   // 下载 + 解密
}
val plain = bytes ?: run { Box(modifier); return }      // 未就绪 / 解不开：留空位
AsyncImage(
    model = ImageRequest.Builder(context).data(plain)   // 明文交 Coil 内置 ByteArray 通路
        .memoryCacheKey("$url#${spec.fingerprint()}")
        .build(),
    contentDescription = contentDescription,
    contentScale = contentScale,
    modifier = modifier,
)
```

四条硬约束（都属"写错了不报错、只是图变灰"那一类，所以写进文档而不是指望 code review）：

| 约束 | 原因 |
|---|---|
| **输入侧**嗅探只认 `RIFF…WEBP` / `\x89PNG` / `GIF8`，**不认 JPEG 的两字节魔数** | 两字节太短，随机密文有概率撞上，会把密文送去解码；站点 worker 的判定也是这么定的 |
| **产物侧**另用一套口径：上面三种 **+ JPEG 的 `FF D8 FF`** | 这一步回答的是"刚才解对了吗"（已确知有密文、也确知 key 口径），3 字节够强。**混用会把刚解出来的 JPEG 判死**——2026-11-16 实测到的正是这个 bug：下载成功、日志 `raw=270080`、界面永远空块 |
| `padding` 按站点真实口径配：站点自己补块 + 按长度截断时必须 `padding:"none"` + 按 `FF D9` 截断 | 示例短剧源的密文**不是** PKCS7 补的（站点 WebCrypto 只给 PKCS7，它反过来做"补一个块再截断"），照抄 PKCS7 会直接解不通；反过来，站内真按 PKCS7 补时配 `none` 会留下 1–15 个废字节 |
| 缓存**解密后的字节**，键里带规则指纹（`algo/敲key/iv/padding` 的 hashCode）+ 密文 URL | 否则每次滚动解一遍；key 轮换后旧缓存也要能自然失效。当前是 24 条内存 LRU，不做磁盘缓存 |
| 解密失败**只降级这一张图** | 图片失败不该影响列表/详情/播放（`W004` 码已定义但**尚未实现**：当前是静默留空位，没有任何提示） |

**图片请求带哪些头（2026-11-16 落地口径）**：当前实现把 `runtime.headers` 一并带给图片请求（示例短剧源实测 4 个头、
`示例图片域` 正常出图）。文档早先设想过"别把 API 头发给图片域名"（担心 CORS 预检）——**实测没这个问题**，
先把简单路径走通；真遇到某站因为多带的头触发预检/403，再单开 `runtime.imageHeaders`（该字段尚未定义，属
`docs/03 §10.1` 那族问题），**不要为了这条路去改 API 头的语义**。

**桌面端多一处**：Coil3 在 JVM 上默认走 `OkHttpNetworkFetcher`。图片的取字节用**图片专用**的 `HttpFetcher`
（`HttpFetcher(createHttpClient())` 单独一个实例），与 API 的 client 分开——复用同一个 client 会把 API 请求
卷进图片链路（表现为所有 JSON 都"解析失败"，且很难查）。

**实测口径**（2026-11-15，示例短剧源的封面）：
密文 174816 字节 → PKCS7 解出 174813 字节 → `FF D8 FF E0 … FF D9`、1086×1448 JPEG，可正常渲染。
同一张图在 `示例图片域` / `示例图片域二` / `示例图片域三` 与 webp 转码域 `备用图片域/<path>.webp`
上都是密文，**没有"换域名/换格式拿明文"的捷径**。

### 8.7.2 通用加解密引擎（M6.2，请求参数 / 响应体 / 单字段，2026-11-16）

配置口径见 `docs/03 §3.3`。这一节只说"为什么这么摆"。

**引擎放在 `core:query`，不放 `core:source` 也不放 `render`**。三个消费方：

| 消费方 | 要什么 |
|---|---|
| `core:config` | 编译期把 `runtime.crypto` 的默认值合进各挂点，并做参数合法性检查（算法白名单、key/iv 长度） |
| `core:source` | 运行期在 `strip` 之后解响应体、在发请求之前加密参数 |
| `core:query` 自己 | `TransformChain` 的字段级解密（它就在 `core:query` 里） |
| `render` | 图片解密（§8.7.1）——顺带复用，所以原先两份 `ImageDecryptActual.kt` 被删掉 |

放在最底层的 `core:query`，上面前三家都能 `api(project(":core:query"))` 直接引用，不需要新增模块。

**`javax.crypto` 只有两份 actual，内容完全相同**（`CryptoBlock.kt` 的 androidMain / jvmMain）。CBC/ECB/CTR/GCM
的 `Cipher` 调用在两端一字不差，所以不抽 `commonMain` 的 expect 接口层再多一级；`expect fun blockCrypt(...)`
只暴露"算法 + key + iv + padding → 字节"，上层 `CryptoCodec` 是纯 common 逻辑。

**base64 / hex 不用 `java.util.Base64`**，改纯 Kotlin 实现。两个原因：

1. Android 上 `java.util.Base64` 是 **API 26+**（`android.util.Base64` 又只在 Android 有），纯 Kotlin 一份代码两端一致；
2. `CryptoCodecTest` 跑在 `jvmTest` 上，纯 Kotlin 实现不会因为"测试跑在 JVM、实机跑在 ART"而掩盖差异。

**编译期烘焙，运行期只查表**。做法与 §1 的 L2→L3 同源：`ConfigCompiler` 在编译时把
`runtime.crypto` 合并进每个挂点，产出 `CryptoOptions`（不可变的 `algo/key/iv/padding/output` + `fingerprint`），
运行期不再检查"这个挂点缺 key 吗"。合并失败（参数非法、`decrypt.from` 路径编译失败）就**返回 null**，
该挂点当没配——配置错误已经在导入期由 `ConfigValidator` 报过，运行期再抛一次只会把"图变灰"升级成"整页崩"。

**三处顺序是硬约束**（顺序错了不会报错，只会"密文解出来的东西不对"）：

| 位置 | 顺序 | 错位的后果 |
|---|---|---|
| 响应体 | `strip` → **decryptBody** → 解析 | 外壳是明文包装（`VAR=…;` 这类外壳），先解会把外壳一起当密文解 |
| `decrypt.from` | 取路径值 → 解密 → **整体替换 body** | 不替换的话 `root`/`list` 还在按信封结构找，取到的是密文串 |
| 字段 | **decrypt** → `trim` / `prefix` / `rewrite` / 正则 | `prefix: {{imageBase}}` 先拼会把域名和密文粘成一串（`https://img.example.com/<密文>`），解出来不是 URL |

请求侧对应的是 `RequestCrypto.transform(url, body, enc)`：URL query 同名参数替换成密文并 **percent 编码**
（`+` `/` `=` 在 query 里必须转义，否则服务端解码后是另一串字节），JSON body 只改**顶层字符串字段**（v1 不递归，
避免误伤嵌套结构）。

**失败一律静默降级**：解不开就按原值走（响应体原样返回 → 解析失败 → 空列表；字段留空；图片留空位）。
理由与 §4 的"一个字段失败不炸整页"一致。代价是**没有任何提示**——`W004`（"声明了加密但解密失败"）仍是待办，
当前唯一的手工排查方式是拿同一段密文和同一组参数单独试解（`tools/validate_config.py` 用的是同口径）。

**两份实现必须同步**：`core:config/…/ConfigValidator.kt`（Kotlin）与 `tools/validate_config.py`（Python）
互为交叉验证。改一边不改另一边，表现是"示例脚本 PASS、App 导入才发现报错"（或反过来）——这属于本项目的
固定约定，不是建议。

**测试**：`CryptoCodecTest`（10 例，含 `zero` vs `none`、GCM、3DES、坏输入返回 null）、`CryptoConfigTest`（4 例，
烘焙与校验）、`CryptoPipelineTest`（4 例，MockEngine 端到端：整段解密 / 外壳取密文 / 单字段（验证在 prefix 之前）/
请求参数加密）。示例配置 `samples/` 里的短剧示例配置 覆盖图片解密；通用加解密（请求参数加密）由 `CryptoPipelineTest` 覆盖，仓库不再保留 `samples/crypto-demo.json`。

### 8.8 音频后台播放（全端里唯一有结构性差异的一处）

视频可以随界面暂停，音频不行 —— 这是音频与视频在工程上真正的分界。

**手机版视频退后台**（2026-11-18 补）：`AndroidPlayerHost.install()` 注册
`Application.ActivityLifecycleCallbacks`；Activity `onStop`（Home / 锁屏 / 最近任务）时，
只对 `MediaKind.VIDEO` 的 `Media3Player` 调 `pause()`，音频共享实例不进入这条路径。
旋转屏幕 `isChangingConfigurations=true` 时跳过，避免误暂停；回到前台保持暂停态，由用户继续播放。

**手机版音乐后台播放开关**（2026-11-18）：设置页「播放 → 音乐后台播放」，
落 `SettingsKeys.PLAYER_AUDIO_BACKGROUND`，默认开（保持原有 M4.5 行为）。关闭后
Activity `onStop` 调 `AudioSession.pauseShared()` 暂停共享音频实例，并
`requestServiceStop()` 停前台服务、撤通知；服务只停自己，不释放 `AudioSession` 的播放器。
回到前台再点播放，`Media3Player.play()` 在 `AudioControlBus.backgroundPlay=true` 时重新拉起服务。
开关切换即时生效：关闭立即撤通知，打开且音频正在播时立即恢复通知。

```
音频起播
  → Foreground Service（MediaSessionService）
  → 通知栏 MediaStyle：播放/暂停/上一首/下一首
  → 锁屏控制（MediaSession 自动接管）
  → 退出应用不停止（除非用户手动停）
```

要点：

- **`MediaSession` 是唯一控制入口**：通知栏、锁屏、蓝牙耳机按键全走它，
  不要自己写广播接收器（那套在 Android 12+ 已被限制）。
- **Manifest 必须声明** `foregroundServiceType="mediaPlayback"` 与
  `FOREGROUND_SERVICE_MEDIA_PLAYBACK` 权限。
- **音频焦点**：来电或其他 App 起播时自动暂停（`AudioFocusRequest`）。
  这条是"能用"和"像样"的分界线。
- **其他端**：iOS 用 `AVAudioSession`（category `.playback`）+ `MPNowPlayingInfoCenter`；
  桌面端不做后台播放（关窗即停）；Web 受浏览器策略限制，切后台可能被暂停 —— 属已知限制，不承诺。

#### 8.8.1 M4.5 落地形态（2026-11-14，安卓模拟器实测通过）

**顺序必须是"先挪归属，再加服务"**：最初 ExoPlayer 由 `AudioRoute` 的 `DisposableEffect` 持有并 `release()`，
页面一走播放器就没了，服务根本拿不到"还在播的那个实例"。现在归属在 `AudioSession`，服务只是它的一个观察者与遥控端。

```
AudioRoute（commonMain）                core:player（androidMain）          app:android
────────────────────────────          ─────────────────────────           ─────────────────
注册纯 Kotlin 回调到 AudioControlBus ──→ Media3Player.prepare(AUDIO)
 title / isPlaying /                        └→ AudioSession.obtain() 共享 ExoPlayer
 onPrev / onToggle / onNext                  └→ AudioSession.requestServiceStart() ──→ AudioPlaybackService
标题/播放态变化 → refreshEvents ────────────────────────────────────────→ 重发通知（两层 RemoteViews）
通知栏"退出" → exitEvents ──→ AppRoot 清 playing                          ├─ MediaSession（锁屏/蓝牙键）
                                                                          └─ "退出"：releaseShared + stopSelf
```

**四个模块各管一件事，谁也不越界**：

| 模块 | 类 | 只管什么 |
|---|---|---|
| `core:player/commonMain` | `AudioControlBus` | 纯 Kotlin 回调 + 事件计数（`exitEvents` / `refreshEvents` / `requestStop`）。**不含任何 Android 类型**，所以 Compose 路由和 Android 服务都能用它 |
| `core:player/androidMain` | `AudioSession` | 音频 ExoPlayer 的唯一持有者。`obtain()` 复用、`releaseShared()` 是唯一释放入口；`serviceStarter` 由壳层注入，core 不依赖 app |
| `app:android` | `AudioPlaybackService` + `notification_audio.xml` | 前台服务 + 两层通知 + `MediaSession`。按钮 → `AudioControlBus`，不认识站点/详情/曲目结构 |
| `feature:main` | `AudioRoute` / `AppRoot` | 播放列表与切歌（只有路由知道）；`AppRoot` 收 `exitEvents` 退出音频页、换源时 `requestStop()` |

**实测证据**（emulator-5554，Android 9 / API 28）：

- 通知栏两层：第一层 `Jazz: Lagoon I` + 最右 X；第二层 上一首 / 暂停 / 下一首。
- 下一首：`Jazz: Lagoon I` → `Jazz: Forms`，`position` 归零、播放页同步 00:02。
- 暂停：`PlaybackState state=2, speed=0.0, position=25255`，通知键与 App 内那颗键**同时**变成 ▶。
- 退出：通知消失、`Media button session is changed to null`、App 回详情页。
- 离开页面继续播：回详情后 `state=3, position=8989` 仍在推进，通知栏常驻。

**踩过的三个坑**：

1. **`setSmallIcon(applicationInfo.icon)` 会直接崩**：本工程没设应用图标，那个值是 0，
   `startForeground` 抛 `Invalid notification (no valid small icon)`。改成系统资源 `android.R.drawable.ic_media_play`。
2. **app 模块拿不到 `ExoPlayer` 类型**：core:player 里写成 `implementation(libs.media3.exoplayer)` 时类型不传递，
   壳层 `MediaSession.Builder(this, player)` 报 `Cannot access class 'ExoPlayer'`。凡是经 `renderToken`/持有者交给壳层的类型都要 `api`。
3. **通知栏的暂停/播放图标不能读 `facade.state`**：页面销毁后心跳与监听器都停了，快照冻在最后一刻。
   所以契约上加了 `PlayerFacade.isPlayingNow()` 直接问播放器（默认实现回落到快照，Android 覆盖为查 `playWhenReady + STATE_READY`）。

**仍未做**：音频焦点（来电/其他 App 起播时自动暂停）、`loop` / `shuffle` 播放模式、
Android 13+ 的 `POST_NOTIFICATIONS` 运行时授权（没授权时服务仍前台、仍出声，只是通知栏看不见）。


### 8.8 搜索历史与观看历史（2026-11-18）

两条都**按源分开存**——同一部作品在不同站的 id 不通用，同一个关键词在不同站的语义也不同；
共用一份只会得到"点了打不开"的列表。存储键见 `core:storage` 的 `SettingsKeys`：
`search.history.<sourceId>`、`history.source.<sourceId>`，外加一份 `history.sources` 索引。

**为什么需要索引**：`AppSettings` 只有 `getString/putString`，没有"枚举所有键"。
历史页要按源分组展示，就得先知道"哪些源有历史"，否则只能遍历 catalog 去猜（删掉的源还会漏）。
所以每次写入/清空都顺手维护一份 `\n` 分隔的源 id 列表；清空到空时把它一起摘掉。

**编码**：没有 JSON 依赖（`feature:main` 没上 serialization 插件），用分隔符拼串：
搜索历史一行一个词、`\n` 分隔；观看历史一条一行、`\u001e` 分隔记录、记录内 `\u001f` 分隔 8 个字段
（`itemId / 标题 / 封面 / kind / 分组名 / 集号 / 数组下标 / 序号`）。
写入前把内容里的分隔符与换行压成空格——标题里出现换行是常事，不做这一步一条记录会被劈成两条。
读取时字段数 < 8 直接丢弃该条，坏记录不连累整页。

**排序用序号不用时间**：`commonMain` 里拿不到"当前时间"，而这里只需要"谁更新"。
`record()` 取全源最大序号 + 1，天然单调，跨平台也不需要引 `kotlinx-datetime`。

**"点历史直接接着看"怎么做到**：
历史只存"看到第几张 / 第几集"，**不存播放秒数**——秒数仍由 `ProgressStore`（键 `源|条目|集号`）负责，
图片位置仍由 `image.progress.<源>.<条目>` 负责。点条目时先取一次详情（查看器要整串 id、播放器要选集，
这些只在详情响应里），再组 `PlayTarget` 直接进 `ImageViewer` / `PlayerRoute`，
`selected` 设成该详情 summary 让返回落在详情页。

**不改顶栏的源**：条目属于别的源时，用 `foreignSession`（按 `SourceEntry` + 同一个 `HttpClient` 临时 `UmpSession.of`）
服务 `selected / playing / viewing` 三个分支；`currentId` 与下拉一行不动。
`activeSession` / `activeSourceId` 是"实际在用的会话与源"，图片进度键、内页懒取、解密规则、`ProgressStore` 键
全部跟着它走；关掉详情（最后一个跨源分支）或手动换源时清空 `foreignSession`。
这样"点历史"与"换源"是两件互不影响的事：前者只影响这一次打开，后者是用户的显式选择。

**已知取舍**：
- 源被删掉后，它的历史不显示（配置读不到，点开只会报错）；没有做"灰色标记已失效"。
- 单源保留 30 条、搜索词 12 个；同一条目只留最新一条并置顶（不给同一部剧留一串集数）。
- 清空只有"按源清空 + 二次确认"，单条删除未做。

回归用例：`feature/main` 的 `HistoryStoreTest`（按源隔离 / 同条目去重置顶 / 标题含分隔符不劈条 / 清空同时摘索引）。


### 8.10 Android 4.4.2 TV 壳（独立原生 View，2026-11-18）

TV 不满足“同一套 Compose UI”的前提：Compose UI 1.9 / Media3 1.8 / Coil 3.3 / core-ktx 1.16 的 AAR 全部是 `minSdk=21`，4.4.2 是 API 19，manifest merger 直接拒绝。因此 `:app:tv` 是独立壳：

**保留的共享层**：`core:model` / `core:query` / `core:config` / `core:source` / `core:storage` 纯 Kotlin 代码直接编译进 TV；`SourcePipeline`、`CompiledSchema`、`PlayTarget`、`AppSettings` 的语义与手机完全一致。

**替换的层**：

| 手机版 | TV 4.4 |
|---|---|
| Compose UI | 原生 `View`：`ListView` / `GridView` / `ImageView` / `TextView` / `FrameLayout` |
| Media3 ExoPlayer | ExoPlayer2 2.19.1（core/hls/ui） |
| Coil 3 | OkHttp 3.12 取字节 + 可选 `runtime.imageDecrypt` + `BitmapFactory` 下采样 |
| Ktor / OkHttp4 | OkHttp 3.12.13 + Okio 1.17.6，`core:source` 里 `exclude(group="io.ktor")` |
| Media3 后台音频 + 通知 | 无 Service、无通知；`onPause` 直接暂停 |

**页面栈**：单 `TvMainActivity` + `TvScreen` 对象栈。`TvHost` 定义导航（源 / 首页 / 详情 / 图片 / 播放 / 历史 / 设置 / 搜索 / 源管理），每个页面实现 `view/onShow/onHide/onPause/onResume/onBack/onKey/requestInitialFocus`。返回键先交给当前页，页面返回 `false` 才弹栈；栈空才 `finish()`。

**焦点**：4.4 盒子对 `GridView` 的 OK 映射不一致，列表额外挂 `OnKeyListener`，在 `ACTION_UP` 且 `keyCode=DPAD_CENTER/ENTER` 时按 `selectedItemPosition` 走 `performItemClick` 兜底；所有可操作控件显式 `isFocusable=true` 并配 `StateListDrawable` 焦点背景。

**图片**：图集仍走 `episodes.lazyItems`（详情只拿 id 表），查看器翻到第 N 张才 `pipeline.resolvePendingTrack` 解析直链；设置 N（0–8，默认 3）表示“当前张之后预加载 N 张”——看第 1 张预取 2/3/4，看第 15 张预取 16/17/18，只向后。直链解析后立即下载字节进 12MB LRU，显示时才解码；Bitmap 缓存上限为最大堆的 1/8（`largeHeap=true`）。

**历史**：TV 用 `TvHistoryStore`，键格式与手机 `HistoryStore` 一致（`history.source.<源id>`、`search.history.<源id>`、`history.sources`）。当前首轮只展示**当前源**历史；点条目用 `DetailScreen(autoOpen=true)` 直接打开上次那张图/那一集，不改当前源。跨源历史完整对齐手机版的 `foreignSession` 尚未做。

**TLS**：4.4 系统根库缺 Let's Encrypt 新根。TV 壳把 ISRG Root X1/X2、GTS Root R4 放 `res/raw`，`TlsSupport` 用系统 `TrustManager` + 内置根做复合校验，并用 Conscrypt 提供 TLS 1.2。

**构建**：`:app:tv:assembleDebug`；产物 `app/tv/build/outputs/apk/debug/tv-debug.apk`；`aapt2 dump badging` 应显示 `com.vi.ump.tv`、minSdk 19、targetSdk 19、`native-code: 'armeabi-v7a' 'x86'`。

### 8.9 新增一个端的操作清单（4 步）

1. **打开 target**：在相关 `build.gradle.kts` 的 `kotlin { }` 里加 `iosArm64()` / `wasmJs()` 等（已有的 `androidTarget()` / `jvm()` 不动）。
2. **补 6 个 actual**：允许先写"占位实现"（抛 `UnsupportedPlatformException` 并在 UI 层提示），
   不必一次做全 —— 但**契约必须先对齐**，否则后续改动要返工。
3. **加入口**：新增 `:app:<platform>`，内容只有窗口/Activity 与 `AppRoot()` 调用，不写业务。
4. **验证**：先跑 `core:query` / `core:config` 的单测（纯逻辑，最容易过）；
   再做冒烟："导入配置 → 首页出图 → 进详情 → 试播放"。

**禁止**：为了省事在 `commonMain` 里写 `if (platform == X)`。
平台判定只能走 `PlatformInfo`，且只在 UI 适配层使用（列数、输入方式、是否显示"桌面播放器待接入"）。

> 从"680ms 上下"降到 **190ms**——差的那 200~400ms 就是逐字段统计与响应预览的拷贝。

### 9.1 删除后的排错路径

两块都删掉之后，"配置能不能用"这件事由三条 App 外/App 内路径分担，没有一条依赖 trace 或沙箱：

| 手段 | 位置 | 能回答什么 |
|---|---|---|
| 配置体检 | 设置页「配置体检」 | `ConfigCompiler` 的 issues：字段缺失 / 类型错 / 路径不合法，带 `$` 路径与原因 |
| 外部校验 | `python tools\validate_config.py <file>`（生成配置后必过） | 结构、必填项、资源引用是否合规，不依赖任何运行期状态 |
| 首页实际出数 | 首页 + 详情页 | 运行期是否真出内容；0 条、字段取错会表现为空列表或占位标题 |

**这是明确的取舍**：运行期"结构合法但 0 命中"这类问题，现在没有 App 内的独立探针，
表现为首页空着，需要回到配置里逐字段核对（`root` / `list` / `fields` 路径）。
如果将来又需要"跑一次看结果"的入口，从上面的 archive 副本恢复即可，不必重写。

## 10. 持久化（`core:storage`）

### 10.1 SQLDelight 表设计

```sql
CREATE TABLE source (
    id TEXT NOT NULL PRIMARY KEY,        -- meta.id
    name TEXT NOT NULL,
    raw_json TEXT NOT NULL,              -- 原始配置文本（用于导出/重新校验）
    enabled INTEGER NOT NULL DEFAULT 1,
    sort_order INTEGER NOT NULL DEFAULT 0,
    imported_at INTEGER NOT NULL,
    last_error TEXT
);

CREATE TABLE history (
    source_id TEXT NOT NULL,
    media_id TEXT NOT NULL,
    title TEXT NOT NULL,
    poster TEXT,
    kind TEXT NOT NULL DEFAULT 'video',      -- video | audio | image
    track_index INTEGER NOT NULL DEFAULT 0,  -- 第几集 / 第几曲 / 第几张
    position_ms INTEGER NOT NULL DEFAULT 0,  -- 视频/音频进度；图片恒为 0
    duration_ms INTEGER NOT NULL DEFAULT 0,
    updated_at INTEGER NOT NULL,
    PRIMARY KEY (source_id, media_id)
);

CREATE TABLE favorite (
    source_id TEXT NOT NULL,
    media_id TEXT NOT NULL,
    title TEXT NOT NULL,
    poster TEXT,
    kind TEXT NOT NULL DEFAULT 'video',
    created_at INTEGER NOT NULL,
    PRIMARY KEY (source_id, media_id)
);

CREATE TABLE search_history (
    keyword TEXT NOT NULL PRIMARY KEY,
    searched_at INTEGER NOT NULL
);
```

**要点**：`source.raw_json` 存原文而非编译产物。理由：
① 编译产物不可序列化回配置（会丢注释与未知字段）；
② 版本升级后可重新编译；
③ 导出功能直接拿原文。

### 10.2 脏数据处理

配置被删除后，`history` 里对应的记录**不删**，而是在查询时通过 `SourceRegistry` 判断源是否仍存在，UI 标记"源已失效"。
理由：删源是误操作高发场景，保留记录才能恢复。

## 11. 安全与性能

### 11.1 安全清单

| 威胁 | 措施 |
|---|---|
| 配置指向本地/私有地址 | scheme 白名单（仅 `http`/`https`）；`localhost`/`127.0.0.1`/`10.x`/`192.168.x` 在编译期告警 |
| 明文流量 | `allowCleartext=false` 时拒绝 `http`，网络安全配置只放行配置声明的域 |
| 配置炸弹 | 体积 ≤1MB、深度 ≤20、`list` 展开上限 500 条/页 |
| ReDoS | 正则长度 ≤200 字符；`from` 文本长度 ≤2MB；不用灾难性回溯写法（长度上限硬挡） |
| JS 注入 | **不实现 JS 引擎**，从根上消除 |
| 数据外泄 | 调试导出自动脱敏 `Cookie`/`Authorization`/手机号/身份证 |
| WebView | 若 `action=link` 用系统浏览器，不在应用内加载任意网页 |

### 11.2 性能预算

| 指标 | 目标 |
|---|---|
| 首页首屏（有缓存） | < 300ms |
| 首页首屏（冷启+网络） | < 1.5s |
| 滚动帧率 | 稳态 60fps（低端机 ≥ 50fps） |
| 配置编译耗时 | < 50ms（1MB 配置，一次性，放 IO 线程） |
| 内存（feed 20 条 + 图片） | < 120MB |

实现手段：L3 预编译、`key` 稳定、图片 Coil 缓存、IO 线程解析、环形 trace 缓冲。

## 12. 关键决策速查表

| 问题 | 决定 | 代价 |
|---|---|---|
| 是否支持 JS | 否 | 少量站点无法纯声明式解析 |
| 是否支持任意 UI DSL | 否 | 布局只能用布局库里的 10 种 |
| 配置存原文还是编译产物 | 原文 | 启动时重新编译（<50ms，可接受） |
| 详情/播放页是否配置驱动排版 | 部分（只给数据源与少量参数） | 灵活性略低，交互质量高 |
| 多源搜索是否支持 | 否（`flags.multiSourceSearch` 已删，2026-11-16） | 一次只搜当前源，无法横向对比多个站点 |
| 搜索入口何时出现 | `enableSearch=true` **且** `resources.search` 非空 | 只写开关不配资源时按钮不出现（否则点进去是空页） |
| 源标识色怎么定 | `meta.color` → 显式 `theme.primary` → 客户端自动分配（按 id 落色相，再用黄金角试探，与其它源色相差 ≥40°） | 显式同色允许共用；只有自动分配去重（见 `SourcePalette`） |
| 已选源是否打勾 | 否，用该源自己的颜色 | 勾和源名抢同一行宽度，还容易被误读成"已收藏"；颜色只回答"现在用哪个源" |
| 主题主色是否随源 | 是 | 作者显式配过 `theme.primary` 就尊重作者；仍是默认 `#FF6B35` 时用该源标识色兜底 |
| 默认只允许 https | 是 | 少数老接口需用户显式开 `allowCleartext` |
| 多端是否共用一套 Compose UI | 是（全部在 `commonMain`） | 播放器与少量系统能力需每端实现 |
| 配置是否感知平台 | 否（见 `docs/03` §16） | 平台能力差异由 `capabilities` 承担 |
| 图片走播放器还是查看器 | 查看器（`core:ui`） | 图片无"播放"语义；混进播放器会让纯图片源被迫依赖解码器 |
| 音频与视频共用一个 `PlayerFacade` 吗 | 共用 | 只是 `kind` 不同；但音频额外需要 Service + `MediaSession` |
| XML / RSS 这类非 JSON 响应怎么支持 | `responseType=text` + `listSplit` 文本分条，字段复用 `regex` 抽取器，**不引入 XML 库** | 深度嵌套或依赖命名空间的 XML 需要逐条调正则；文本通路没有 `hasMore` |
| 站点级测试数据从哪来 | 只有 `samples` + `samples/fixtures` 一个来源，测试禁止内联假 JSON | 测试依赖仓库文件，`commonTest` 读不到磁盘，只能放 `jvmTest`（见 §5.2.1） |
