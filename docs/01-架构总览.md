# 01 · 架构总览与模块拆分

> 本文回答三个问题：**这个东西本质上是什么？**、**拆成哪些模块？**、**模块之间怎么串起来？**

---

## 1. 本质：三个"固定"夹住一个"可变"

传统影视 App 的做法是：每个站点写一套 `Api` 类 + 一套解析逻辑，站点一变就要发版。
vi-ump 的做法是把**变化的部分全部赶到配置文件里**，代码只保留三个固定层。

支持三种媒体：**视频 / 音频 / 图片**。三者共用同一套外壳（`MediaSummary` + `TrackGroup/Track`），
用 `kind` 区分，只在"详情页分支、播放/查看器、进度语义"三处产生差异 —— 不出三套模型。

```
        ┌─────────────────────────────────────────────┐
        │  固定层 1：域模型（Data Contract）           │   ← 代码定义，永不变
        │  MediaSummary / MediaDetail / TrackGroup ... │
        └─────────────────────────────────────────────┘
                              ▲
                              │  映射（配置提供）
        ┌─────────────────────────────────────────────┐
        │  可变层：外部数据源（任意 JSON / HTML / 文本）│   ← 用户配置决定
        └─────────────────────────────────────────────┘
                              │
                              ▼
        ┌─────────────────────────────────────────────┐
        │  固定层 2：抽取与变换引擎（Extractor/Transformer）│
        └─────────────────────────────────────────────┘
                              │
                              ▼
        ┌─────────────────────────────────────────────┐
        │  固定层 3：布局库 + 渲染引擎（Layout Palette）│  ← 代码定义，永不变
        └─────────────────────────────────────────────┘
```

**关键结论**：App 代码只认识域模型，永远不为新站点写代码。
新增一个站点 = 新增一份 JSON；删掉一个站点 = 删一份 JSON。

这就是"用户导入配置文件自行决定和渲染"的工程化表述。

## 2. 三层编译模型（配置即程序）

配置不是"读进来随手用"，而是像编译器一样**分三级处理**，把运行时的解析开销全部前移到加载期：

| 层级 | 名称 | 形态 | 谁产出 | 校验内容 |
|---|---|---|---|---|
| L1 | **Raw** | `JsonElement` / 原始文本 | 用户导入 | 体积、JSON 语法 |
| L2 | **Document** | `UmpConfig`（sealed data class，kotlinx.serialization） | `ConfigLoader` | 结构合法性：字段类型、枚举值、必填项 |
| L3 | **Compiled** | `CompiledSchema`（路径 token 化、模板片段化、字段映射表、页面树） | `ConfigCompiler` | 语义合法性：引用存在性、循环引用、路径语法 |

**为什么必须分三级**：

1. **L2 用 kotlinx.serialization 反序列化**，结构问题在加载期就报错，而不是运行时崩溃；
2. **L3 预编译路径字符串**：`"$.data.items[*].vod_name"` 每次渲染都重新解析会是几千次/秒的开销。编译期把它变成 `List<PathToken>`，运行期只做遍历；
3. **L3 校验引用完整性**：页面引用了不存在的 `feed`、播放引用了不存在的字段，在这时就报错并精确定位到 JSON 的行/字段路径，而不是用户点了播放才白屏。

**错误定位示例**（这是调试体验的关键，实现原理见 04 文档）：

```
[配置校验失败] resources.feeds.hotList.fields.poster.from
  → JSONPath 语法错误：`$.[0]` 非法，应为 `$[0]`
  → 位置：第 42 行
```

## 3. 核心设计取舍（为什么这样做）

### 取舍一：受控布局库 vs 通用 UI DSL

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 通用 UI DSL（配置描述任意控件树） | 理论上无限灵活 | 布局质量不可控、嵌套深性能差、配置学习成本极高、错误无法定位、无障碍/适配全部失守 | ❌ 不采用 |
| B. 受控布局库（枚举 LayoutType + slot 参数） | 每个布局都是精调过的真实组件，性能与体验可保证，配置只需填参数 | 灵活性有边界 | ✅ **采用** |
| C. 完全固定 UI（只换数据） | 最简单 | 无法满足"自主决定页面渲染"的核心诉求 | ❌ 不采用 |

**落地方式**：`LayoutType` 枚举（`poster_grid`、`banner_hero`、`row_cards`、`list_linear`、`category_filter`、`detail`、`track_panel`、`gallery_grid`、`image_viewer`、`video_player`、`audio_player`、`search`、`tabs`），
每种类型有明确的 **slot 契约**（哪个字段放图、哪个字段放角标、列数、比例、间距），配置只能选择类型 + 填 slot。
新增布局 = 发版加一个 Composable（一次性成本），而不是让配置去拼像素。

### 取舍二：不做 JS 引擎

TVBox 生态里大量配置依赖 Spider（JS）实现，能力强但代价是**执行任意代码**——不可审计、不可控、崩溃无法定位，也带来安全风险。

vi-ump v1 明确不支持 JS。取而代之的是把 90% 的常见逻辑用**声明式原语**覆盖：

- 拼接 → `template`（`{{baseUrl}}/play/{{id}}.m3u8`）
- 切分 → `delimited`（`$$$` / `#` / `$` 多级分隔）
- 条件 → `map`（枚举映射）+ `default`（兜底）
- 正则改写 → `rewrite`（`s/xxx/yyy/`）

这覆盖了绝大多数影视接口的形态。真正需要 JS 的站点，作为已知限制记录，不做承诺。

### 取舍三：KMP 的物理模块数量——渐进拆分

多模块是长期正确，但一次性拆 11 个模块会让首次构建、依赖排查成本过高。
因此**逻辑分层一次讲清，物理模块分期落地**（见第 5 节 Stage 1 → Stage 3）。

## 4. 模块拆分与职责

### 4.1 模块清单

| # | 模块 | 类型 | 职责（一句话） | 不做什么 |
|---|---|---|---|---|
| 1 | `:app:android` | Android Application | 壳：Application、Activity、权限、深链入口 | 不写业务逻辑 |
| 2 | `:core:model` | KMP Library（零第三方依赖） | 域模型 + 配置模型 + 所有枚举 | 不含任何 IO |
| 3 | `:core:common` | KMP Library | `StageResult`、日志、URL 工具、协程调度器、DI 模块 | 不含业务语义 |
| 4 | `:core:query` | KMP Library（可在 JVM 单测） | **抽取引擎**：JSONPath/正则/分隔符/模板/CSS；**字段变换器** | 不发起网络 |
| 5 | `:core:config` | KMP Library | 配置装载、校验、编译（L1→L3）、版本迁移、内置模板 | 不渲染 UI |
| 6 | `:core:source` | KMP Library | HTTP 引擎 + **数据管线执行**（JSON 与文本分条双通路）+ 源注册表 + 内存缓存 | 不关心页面长什么样 |
| 7 | `:core:storage` | KMP Library | SQLDelight：历史/收藏/配置仓库/缓存条目；设置项 | 不解析业务数据 |
| 8 | `:core:player` | KMP Library（expect/actual） | 播放器门面 + `PlayResolver`（直链/解析接口） | 不做 UI 手势 |
| 9 | `:core:ui` | KMP Library + Compose | 设计系统：`UmpTheme`、`PosterCard`、`StateView`、骨架屏 | 不含页面逻辑 |
| 10 | `:render` | KMP Library + Compose | **渲染引擎**：`PageNode` 树 → Compose；布局库；Item 模板 | 不发请求 |
| 11 | `:feature:main` | KMP Library + Compose | 页面级状态、导航、各 feature 分包（home/detail/player/search/settings）。**现状：没上 ViewModel**——状态就是 `AppRoot` 里的 `remember` + 参数下传（`docs/04 §7.1`～`§7.3`） | 不直接碰 HTTP |

### 4.2 依赖方向（严格单向，禁止反向与横向）

```
:app:android  /  :app:desktop          （多端只换入口，业务代码共用 AppRoot）
     │
     ▼
:feature:main ──► :render ──► :core:ui ──► :core:model
     │                │
     │                └──► :core:source ──► :core:config ──► :core:query ──► :core:model
     │                        │                │
     │                        ▼                ▼
     └──► :core:storage   :core:common    :core:common
              │
              ▼
         :core:player ──► :core:model
```

三条硬规则：

1. **`core:model` 是最底层，不依赖任何模块**（保证域模型可以给任何层引用而不形成环）。
2. **`feature:*` 之间禁止互相依赖**，跨页面交互通过 `Navigation` 回调 + `route` 参数传递，不做直接引用。
3. **`render` 不认识 `HttpClient`，`core:source` 不认识 `Composable`**。两边的接口是 `CompiledSchema` + 域模型，这是"配置语义"的唯一交汇点。

## 5. 物理落地分三期

### Stage 1（首个可运行版本，6 个模块）

```
:app:android
:core:model
:core:engine     ← config + query + source 先合并（三者迭代期强耦合，拆开反而拖慢）
:core:platform   ← storage + player + common
:core:ui
:render
:feature:main
```

理由：配置编译器和抽取引擎在早期会反复改接口，合在一个模块里改起来不用同步发版。

### Stage 2（功能稳定后，9 个模块）

拆出 `:core:query`（独立可 JVM 单测）、`:core:config`、`:core:source`。

### Stage 3（11 个模块）

再拆 `:core:common`、`:core:storage`、`:core:player`；`feature:main` 按页面拆成 `feature:home` / `feature:detail` / `feature:player` / `feature:search` / `feature:settings`。

> 当前已生成的工程骨架按 **Stage 3 的目标结构**建目录（文件是占位/骨架），
> 可以先按 Stage 1 的思路删减 settings.gradle.kts 中的 `include`，后续逐个开启。

## 6. 一次完整请求的数据流（逐层打点）

以"打开首页 → 点进详情 → 播放第 3 集"为例：

```
① 首页 Tab 切换
   feature:main（现状：`AppRoot` 的 `remember` 状态 + `HomeRoute`，没有 ViewModel）
     → source.getFeed("hotList", params={category:"1", page:1})
       → config 已编译的 ResourceSpec
         → HttpEngine: template.url 渲染 → GET https://api.example.com/api/list?cat=1&page=1
           → query: root="$.data" → list="$.items[*]" → 每个 item 按 fields 映射
             → 域模型 List<MediaSummary>
     → render: PageNode(poster_grid) + items → Compose LazyVerticalGrid

② 点击卡片
   action: {type:"openDetail", id:"{{item.id}}"} → Navigation → DetailRoute(id)

③ 详情页
   detail 资源按单对象映射 → MediaDetail（含 trackGroups；kind 决定渲染分支）
   track_panel 布局渲染线路 Tab + 选集网格（音频=播放列表，图片=gallery_grid）

④ 播放第 3 集
   PlayRequest(url="https://cdn.example.com/x.m3u8", headers={Referer})
   → PlayResolver：strategy=DIRECT → 直接传给 player
   或 strategy=RESOLVER → 请求解析接口 → 抽取真实地址 → 再传给 player
   → core:player（Android: Media3 ExoPlayer）播放；进度写 storage:history
```

每一层都可以被 `DebugSession` 打点（设计稿口径）；实际实现里这套采集在 M5 收尾时已被**整体删除**，
配置沙箱（`UmpSession.sandboxList / sandboxDetail`）随后也一并删除，配置排错只剩"配置体检"
（`ConfigCompiler` 的 issues，带路径与原因）这一条 App 内手段（见 04 文档 §9 的决策记录）。

## 7. 平台策略（KMP 视角）

**目标：一份配置、一套 Compose UI 跑在多端；平台差异收敛到 6 个 `expect/actual`。**

| 能力 | commonMain 抽象 | Android（当前） | 桌面 (JVM) | iOS | Web |
|---|---|---|---|---|---|
| HTTP | Ktor `HttpClient`（engine 按平台注入） | OkHttp engine | OkHttp / CIO | Darwin | Js |
| HTML 解析 | `expect HtmlParser` | Jsoup | Jsoup | SwiftSoup / 正则降级 | 正则降级 |
| 播放器 | `expect class PlayerFacade` | Media3 ExoPlayer | VLCJ / JavaFX Media | AVPlayer | `<video>` |
| 键值存储 | `expect KeyValueStore` | DataStore | java.util.prefs | NSUserDefaults | localStorage |
| 数据库 | SQLDelight（common 定义 .sq） | AndroidSqliteDriver | JdbcSqliteDriver | NativeSqliteDriver | WebWorkerDriver |
| 文件导入 | `expect FileGateway` | SAF | FileDialog | UIDocumentPicker | File API |
| 图片 | Coil 3（天然 KMP） | OkHttp fetcher | OkHttp fetcher | Ktor fetcher | JS fetcher |

**三条原则**：

1. `commonMain` 里不允许出现 `android.*` / `java.*` 引用；
2. 平台差异一律走 `expect/actual`，`actual` 只放在对应 `xxxMain`；
3. 新增一个端 = 补齐该端 actual + 打包配置，**不改 commonMain 业务代码**。

> 完整矩阵、各端打包命令、响应式断点、移植成本评估见 **`docs/06-多端适配方案.md`**。

当前工程已落实：所有 `core:*` 与 `render`/`feature:main` 均启用 `androidTarget + jvm`，
`app/android` 与 `app/desktop` 两个入口共用 `AppRoot()`。

## 8. 架构风险与对策（先说清楚）

| 风险 | 说明 | 对策 |
|---|---|---|
| 配置质量参差 | 用户写的 JSON 错漏百出 | ① 「配置体检」列 issues（带路径与原因，原调试器与沙箱均已删除） ② 校验器 `validate_config.py` 给出精确路径 ③ 内置样例 |
| 布局类型不够用 | 配置者想要新排版 | 布局库按真实场景扩充；`slots` 参数（列数/比例/间距）先覆盖变体 |
| 反爬 / 加密 / JS | 部分站点无法纯声明式解析 | 明确不支持；文档标注为已知边界，不做灰色功能 |
| 性能 | 大列表 + 频繁解析 | L3 预编译、分页 20/页、图片走 Coil 缓存、解析在 IO 线程 |
| 安全 | 配置可指定任意 URL | scheme 白名单、体积/深度上限、禁止本地路径、正则长度上限 |
