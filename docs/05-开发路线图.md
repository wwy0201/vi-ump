# 05 · 开发路线图

> 原则：**先让"配置能编译、数据能抽出"这件事单独跑起来**，再往上接 UI。

> **M4.8 落地记录（2026-11-11，桌面端实测）**
>
> 用户的疑问是"每个栏目可能有分页数据，现在好像没有处理"。排查下来分三层，**只有第一层是渲染层**：
>
> | 层 | 状态 | 结论 |
> |---|---|---|
> | 渲染/触发（`GridPagingEffect` / `RowPagingEffect`） | 早已接通 | 滚到距末尾 3 条内就 `onLoadMore`，日志实测确实发了第 2 页请求 |
> | 取数（`SourcePipeline.list`） | **有洞，已补** | 原来只 `("page" to page)`：`paging.param`（如站点要 `offset`）、`startAt`（如第一页是 0）、`step`、`mode:offset` **全部不生效**。现在统一由 `pagingVars()` 翻译（`docs/04 §5.2.3`） |
> | 状态（`HomeRoute` + `UmpSession`） | **两个 bug，已修** | ① 缓存命中把 `page` 写死 1 → 再滚动会重请求第 2 页并**重复追加**；② loadMore 成功后没回写缓存 → 切栏目回来**翻页进度归零**。现在命中用 `hit.page`、loadMore 结果整份 `remember` |
>
> 另加一层**自适应到底**：按 id 去重后"整页都是旧条目"就判 `hasMore=false`。这不是可选优化 ——
> 文本通路的 `hasMore` 只能靠"本次结果非空"（永远 true），没有它就会翻到 `maxPage` 把同一屏复制 N 遍（实测会从 14 条变 70 条）。
>
> **示例视频源的三个栏目没有真分页**（源侧事实，不是代码缺陷）：频道页带 `?offset=15`、`?offset=0&pagesize=30`
> 与不带参数返回的条目集合完全相同；`?page=1|2` 也完全相同，`page=3` 才有 2 条差异（服务端推荐位随机漂移）。
> 所以栏目配置写 `maxPage:5` 只是"留口子"，实际靠去重到底第 3 页自然停：日志
> `page=2 返回=14 新增=1` → `page=3 返回=14 新增=0 判到底=true`。三组 URL 对照与完整日志见 `docs/04 §5.2.4`。
>
> 顺带修掉一个**存量红测试**：`SamplePipelineTest` 里那条"外壳剥离 + 播放地址拼装"用例还在断言播放地址以
> CDN 的 IP 段起头，而配置里的 `rewrite` 早已刻意去掉 IP（IP 绑机房、换网就 403）。断言改成"去 IP 后的域名"，并注明原因。
> 新增 `pagingSpecIsTranslatedIntoRequestVariables` 覆盖分页翻译（响应体仍用 `samples/fixtures` 的接口快照，不造数据）。

#### M7.5 落地记录（桌面端真实播放）

选型 **vlcj 4.8.2 驱动本机 libvlc**，而不是 JavaFX Media / Media3：桌面端只有 Windows 一个目标、VLC 基本已装；
Media3 无桌面版；JavaFX Media 对 m3u8/mkv 支持差。vlcj 只是 libvlc 的 JNA 封装，解封装/解码/字幕/倍速全交给 VLC，
行为等价于"用 VLC 打开这个 URL"。代价是运行期依赖本机 VLC（找不到就降级成占位并提示装 VLC，不黑屏）。

| 落点 | 改动 |
|---|---|
| `gradle/libs.versions.toml` | `vlcj = 4.8.2`、`jna-platform = 5.6.0` |
| `core/player/build.gradle.kts` | `jvmMain` 加 `libs.vlcj` + `libs.jna.platform` |
| `core/player/src/jvmMain/.../PlayerFacade.jvm.kt` | `VlcPlayerFacade` + 保留 `UnsupportedPlayer` 兜底 + `createPlayerFacade()` |
| `app/desktop/.../main.kt` | `SwingPanel` 挂 `renderToken`（AWT `Canvas`），`controlsBelowSurface = true` |
| `render/.../PlayerView.kt` | 新增 `controlsBelowSurface`：控制条放下方常驻（桌面端必需） |
| `feature/.../PlayerRoute.kt`、`AppRoot.kt` | 透传该开关 |

**踩过的坑（两个，都不是可有可无的）**

1. **vlcj 在 Windows 靠注册表找 VLC 安装目录**，这条链路需要 `jna-platform`，而它**不随 vlcj 传递**。
   不补就抛 `NoClassDefFoundError: com/sun/jna/platform/win32/WinReg`，`NativeDiscovery().discover()` 返回 false，
   应用表现为"未找到 VLC"——看起来像接入没生效，其实是缺依赖。
2. **vlcj 的画面是 heavyweight AWT `Canvas`**，由 Compose `SwingPanel` 承载，绘制在 Compose 画布**之上**。
   叠在画面里的控制条（进度条 / 播放 / 倍速 / 全屏）会被视频整块盖住。所以桌面端把控制条改到画面下方常驻
   （`controlsBelowSurface = true`），全屏时同样是"画面撑满 + 下方控制条"。

**解码链路实测（命令行探针，不开窗口）**

| 输入 | 结果 |
|---|---|
| `NativeDiscovery().discover()` | `native=true` |
| `https://cdn.example.com/sample.mp4` | `length=10027`、`state=PLAYING`、`t=151→1152→2151ms` 递增 |
| 示例源在线直链（详情接口拼出、去掉 CDN IP 段） | `length=205000`（=03:25，与 App 内 `剧名_01` 一致）、`state=PLAYING` |

**应用内实测（已确认）**：首页点《示例剧集》海报 → 详情页（22 集）→ 点「播放」，播放页出画面、
时间码 `00:29/03:25` → 隔 10 秒再截为 `01:32/03:25`，画面内容同时切换（场景变、字幕人名变），
进度条推进，状态「播放中」。控制条渲染在画面**下方**（`<10s｜暂停｜1.0x｜全屏｜10s›`），未被视频面遮挡。

采集过程中确认的两个操作事实，留给以后自动化用：
- `cu.click` 在这台机器上不移动指针（点击无效）；系统级 `SetCursorPos + mouse_event` 有效。
- 截图（2048 宽）与屏幕物理像素（2560×1080）**不是**同一坐标系，按图坐标点击会整体偏。
  可靠做法是 `GetWindowRect` 拿窗口物理矩形，用**窗口内相对比例**（0–1）换算，不依赖缩放比例。

续播点 seek 只在真正起播后做（VLC 在起播之前没有有效位置，提前 seek 会被静默丢掉）。
`capabilities.supportsHeaders = false`：vlcj 要加 Referer 得拼 `:http-referrer=` 的 media option，
当前示例视频源不需要；将来遇到校验 Referer 的源，这里要补。

**坑 3（本轮补上，并已实测修复）**：为了拿视频真实尺寸，一开始在 vlcj 的 `playing` 事件回调里读
`video().videoDimension()`。该回调跑在 **libvlc 事件线程**上，调用 libvlc API 会阻塞它 →
状态永远到不了 `PLAYING`，界面卡「准备中…」+ 黑屏，日志无报错（续播场景必现）。
改成事件回调只做状态标记 + 250ms 独立协程 ticker 读 time/length/尺寸，并顺带在那里做续播 seek。
修复后实测续播 `上次看到 02:58` → 直接跳到 `03:23/03:25` 并正常出画面。

**画面比例（用户反馈项，已修复）**：`PlayerState` 增加 `videoWidth/videoHeight`，
画面容器改用 `state.videoAspect ?: 16:9`，起播后不再画封面图 —— 否则竖屏/4:3 视频在 16:9 容器里留边，
会把下面的封面图透出来（"视频背景里有张海报"）。Android 端在 250ms ticker 里取 `player.videoSize`。
